# 监控与告警

svngod 暴露两组指标，配合 Prometheus + node_exporter 即可覆盖“提交路径、副本一致性、缓存效率”三条主线。

## 1. 采集

### 1.1 服务端 `/metrics`

```yaml
# prometheus.yml
scrape_configs:
  - job_name: svngod
    metrics_path: /_metrics
    static_configs:
      - targets: ["svngod-1:8080", "svngod-2:8080"]
```

`/_metrics` 与 SVN 服务同端口（默认 `/_metrics`，可用 `svngod -metrics=false` 关闭）。**不要**把它暴露到公网：标签里包含仓库名，且没有任何认证。

### 1.2 副本一致性（textfile）

`svnadmin replicas` 可以把“多副本是否一致”写成 Prometheus textfile，交给 node_exporter 的 textfile collector：

```cron
*/10 * * * * svnadmin replicas -verify -quiet -textfile /var/lib/node_exporter/textfile/svngod-replicas.prom --mirror-file /etc/svngod/mirror.json <repo> || true
```

`svnadmin verify` 在发现完整性问题时以退出码 1 结束，也可以把结果写成 textfile 指标（`-textfile`），让定时全量校验出现在告警面板上：

```cron
0 3 * * * svnadmin verify --all-revs --workers 4 -textfile /var/lib/node_exporter/textfile/svngod-verify.prom \
            --mirror-file /etc/svngod/mirror.json <repo> || true
```

指标：`svngod_verify_issues{repo,scope}`、`svngod_verify_ok{repo}`（0/1）、`svngod_verify_duration_seconds{repo}`、`svngod_verify_last_run_timestamp{repo}`。

### 1.3 审计日志

每次提交和修订属性修改**成功后**，服务端向 `svngod` 日志追加一行结构化审计记录：

```text
audit commit mode="dav" repo="demo" rev=123 user="alice" paths=3 add=1 modify=2 delete=0
audit commit mode="bundle" repo="demo" rev=124 user="alice" paths=200 add=200 modify=0 delete=0
audit revprop repo="demo" rev=98 user="ops" set=1 remove=0
audit deny reason="bad_credentials" repo="demo" user="mallory" method="OPTIONS" path="/svn/demo"
audit deny reason="forbidden" repo="demo" user="bob" method="PROPPATCH" path="/trunk/README.txt"
```

- 拒绝记录：凭据错误写 `reason="bad_credentials"`（只记用户名，**不记密码**），authz 拒绝写 `reason="forbidden"`；两者都带仓库、方法与被访问路径，可作为撞库/越权的告警来源。
- 写入点在 `CommitTxn` / `UpdateRevProps` 返回成功之后，因此审计流里的每个 `rev` 都真实落盘；冲突、被 hook 拒绝、503 重试中的提交不会产生 commit 记录。
- 只记元数据（操作者、仓库、修订号、路径计数与增删改分布），**不记**文件内容、提交说明和属性值，可直接投递到 SIEM/日志平台而不泄露仓库数据。
- 用户名与仓库名按 `%q` 转义，标识里的换行或引号无法伪造出第二条记录；未认证操作记为 `anonymous`。
- `mode=dav` 是原生 svn（HTTPv1/v2）路径，`mode=bundle` 是 svngocli 的单请求原子提交通道。
- 采集方式：按行读取服务的 stderr（journald / filebeat / vector），过滤 `audit ` 前缀即可；管理 API 的操作另有 `admin action=…` 记录。

服务端启动时会逐个打开已配置仓库并读取 HEAD，日志中每个仓库一行 `self-check: repository "x" ready (head=… uuid=… segments=…)`；配置错误会立刻以 `NOT READY` 暴露。需要“任一仓库不可读就拒绝启动”时加 `-strict-start`。

## 2. 指标参考

| 指标 | 类型 | 含义 |
|---|---|---|
| `svngod_http_requests_total{method,status}` | counter | HTTP 请求数（按方法/状态码） |
| `svngod_http_request_duration_seconds_{sum,count}` | counter | 所有请求的累计耗时与次数 |
| `svngod_http_request_bytes_total` / `_response_bytes_total` | counter | 请求/响应字节数 |
| `svngod_commits_total` | counter | 已提交修订数（DAV + bundle） |
| `svngod_commit_duration_seconds_bucket{le}` / `_sum` / `_count` | histogram | MERGE（提交）延迟，桶 50ms…30s，可算 p50/p95/p99 |
| `svngod_commit_errors_total{reason}` | counter | 提交失败原因：`out_of_date`、`lease_busy`、`quorum`、`replica_lagging`、`index_conflict`、`lease_lost`、`other` |
| `svngod_upload_inflight` / `svngod_upload_limit` | gauge | 在途上传数与上限 |
| `svngod_bundle_uploads_total` / `svngod_bundle_replays_total` | counter | bundle 上传次数 / 幂等重放次数 |
| `svngod_mirror_healthy{repo,replica}` | gauge | 副本当前是否可达 |
| `svngod_mirror_primary{repo,replica}` | gauge | 该副本是否本进程的主写副本 |
| `svngod_mirror_last_write_seconds{repo,replica}` | gauge | 距上次成功写入的秒数（-1 = 未知） |
| `svngod_block_cache_hits_total{repo}` / `_misses_total` | counter | 修订块缓存命中/未命中 |
| `svngod_segment_cache_hits_total{repo}` / `_misses_total` | counter | 已解码段缓存命中/未命中 |
| `svngod_repo_ready{repo}` | gauge | 启动自检时该仓库是否可读（1/0） |
| `svngod_repo_recovered_total{repo}` | counter | 仓库从不可用恢复为可用的次数（热恢复） |
| `svngod_repo_ready_error{repo,reason}` | gauge | 自检失败原因（`not_found`/`auth_denied`/`network`/`corrupt`/`other`，标签值受控） |
| `svngod_repo_head{repo}` | gauge | 本进程已打开仓库的当前 HEAD |
| `svngod_store_ops_total{store,op}` | counter | 后端操作次数（`file`/`s3` × `get`/`put`/`put_from`/`delete`） |
| `svngod_store_op_errors_total{store,op}` | counter | 后端操作失败数（`NotFound` 不计入） |
| `svngod_store_op_duration_seconds_{sum,count}` | summary | 后端操作累计耗时/次数，可算平均延迟 |
| `svngod_replica_head{repo,member}` | gauge | 各成员报告 HEAD |
| `svngod_replica_verify_issues{repo,member}` | gauge | 各成员校验问题数（-1 = 校验执行失败） |
| `svngod_replica_consistent{repo}` | gauge | 1 = 各成员 head/uuid/索引摘要一致 |
| `svngod_replica_content_objects{repo,member,kind}` | gauge | `replicas -counts` 统计的各成员 texts/chunks/dirs 对象数 |
| `svngod_replica_content_bytes{repo,member,kind}` | gauge | 同上，按对象族统计的字节数 |
| `svngod_replica_last_run_timestamp{repo}` | gauge | 上次副本检查的 Unix 时间（用于新鲜度告警） |

### 2.1 textfile 约定

- 路径固定、按仓库命名：`<textfile 目录>/svngod-verify-<repo>.prom`、`svngod-replicas-<repo>.prom`；目录与 node_exporter 的 `--collector.textfile.directory` 一致；
- 写入是**原子**的（写 `.tmp` 再 rename），失败会清理临时文件，不会留下半个文件；
- 定时任务用 `|| true` 兜底，避免 cron 因非零退出码停止后续仓库；
- 文件只保留最新一次结果，不需要轮转；`mtime` 可作为“任务是否还在跑”的旁证（另有 `last_run_timestamp` 指标）。

## 3. 告警规则示例

```yaml
groups:
  - name: svngod
    rules:
      - alert: SvgodCommitSlow
        expr: |
          histogram_quantile(0.95,
            sum by (le) (rate(svngod_commit_duration_seconds_bucket[10m]))) > 2
        for: 15m
        labels: {severity: warning}
        annotations:
          summary: "提交 p95 > 2s"
          description: "持续 15 分钟；检查后端延迟、租约争用与组提交配置。"

      - alert: SvgodCommitBackendErrors
        expr: |
          sum by (reason) (rate(svngod_commit_errors_total{reason=~"quorum|replica_lagging|lease_busy|index_conflict|lease_lost"}[5m])) > 0
        for: 5m
        labels: {severity: critical}
        annotations:
          summary: "提交因后端问题失败 ({{ $labels.reason }})"
          description: "out_of_date 是客户端冲突，可忽略；这几类说明存储/副本出了问题。"

      - alert: SvgodMirrorUnhealthy
        expr: svngod_mirror_healthy == 0
        for: 5m
        labels: {severity: warning}
        annotations:
          summary: "副本 {{ $labels.replica }} 不可达（仓库 {{ $labels.repo }}）"

      - alert: SvgodMirrorLagging
        expr: svngod_mirror_last_write_seconds > 120
        for: 10m
        labels: {severity: warning}
        annotations:
          summary: "副本 {{ $labels.replica }} 超过 2 分钟没有成功写入"

      - alert: SvgodVerifyFailed
        expr: svngod_verify_ok == 0
        for: 1h
        labels: {severity: critical}
        annotations:
          summary: "仓库 {{ $labels.repo }} 最近一次校验发现完整性问题"
          description: "看 {{ $labels.repo }} 的 verify 日志；副本场景先 `replicas -repair`。"

      - alert: SvgodVerifyStale
        expr: time() - svngod_verify_last_run_timestamp > 172800
        for: 1h
        labels: {severity: warning}
        annotations:
          summary: "仓库 {{ $labels.repo }} 超过 48 小时没有执行全量校验"
          description: "检查 verify 定时任务与 textfile 输出路径。"

      - alert: SvgodReplicaCheckStale
        expr: time() - svngod_replica_last_run_timestamp > 3600
        for: 30m
        labels: {severity: warning}
        annotations:
          summary: "仓库 {{ $labels.repo }} 超过 1 小时没有成功执行副本检查"
          description: "检查 replicas 定时任务（cron/node_exporter textfile）是否还在运行。"

      - alert: SvgodRepoFlapping
        expr: sum by (repo) (rate(svngod_repo_recovered_total[30m])) > 0
        for: 30m
        labels: {severity: warning}
        annotations:
          summary: "仓库 {{ $labels.repo }} 反复恢复（后端不稳定）"
          description: "查看 svngod_repo_ready_error 的 reason 与后端健康。"

      - alert: SvgodReplicaDrift
        expr: svngod_replica_consistent == 0
        for: 20m
        labels: {severity: critical}
        annotations:
          summary: "仓库 {{ $labels.repo }} 的副本不一致"
          description: "运行 `svnadmin replicas -repair`，随后 `verify --all-revs`。"

      - alert: SvgodBackendSlow
        expr: |
          sum by (store, op) (rate(svngod_store_op_duration_seconds_sum[5m]))
            / clamp_min(sum by (store, op) (rate(svngod_store_op_duration_seconds_count[5m])), 0.001) > 0.15
        for: 15m
        labels: {severity: warning}
        annotations:
          summary: "后端 {{ $labels.store }}.{{ $labels.op }} 平均延迟 > 150ms"
          description: "提交慢时优先看 get/put；先排除副本落后与网络。"

      - alert: SvgodCacheMissStorm
        expr: |
          sum by (repo) (rate(svngod_block_cache_misses_total[5m]))
            / clamp_min(sum by (repo) (rate(svngod_block_cache_hits_total[5m]) + rate(svngod_block_cache_misses_total[5m])), 0.001) > 0.9
        for: 30m
        labels: {severity: info}
        annotations:
          summary: "仓库 {{ $labels.repo }} 块缓存命中率 < 10%"
```

审计告警不在 `/_metrics` 里：把服务 stderr 收进 Loki/ELK 后，对 `audit deny` 做计数即可，例如 5 分钟内同一 `user` 的 `reason="bad_credentials"` 超过 20 次，或任一 `reason="forbidden"` 出现在非只读账号上。审计行是单行 key=value，可直接用 `| logfmt` / `kv` 解析，无需正则。

## 4. 值班处置顺序

1. **`SvgodCommitBackendErrors`（critical）**：先看 `svngod_mirror_*`，确认是副本掉线还是法定人数不足；`svnadmin replicas -quiet -verify --mirror-file ...` 看是否漂移；必要时 `-repair-mirror` 补齐，再 `-repair-index`。
2. **`SvgodReplicaDrift`**：`replicas -repair`（先镜像补齐，再逐成员重建索引、清理死覆盖），随后 `replicas -verify` 与 `svnadmin verify --all-revs`。
3. **`SvgodCommitSlow`**：查 `svngod_commit_errors_total{reason="lease_busy"}` 是否升高（多进程争用）；查后端延迟与 `svngod_mirror_last_write_seconds`。
4. **磁盘回收**：`svnadmin gc -dry-run` 先看可回收量，再执行 `svnadmin gc`；大仓库用 `--progress` 观察阶段进度。

## 5. 容量与巡检建议

- 每 6 小时：`svnadmin replicas -verify -quiet -textfile ...`；
- 每天：`svnadmin verify --all-revs --workers 4`（20 万修订约 4 秒；千万级按分片并行）；
- 每周：`svnadmin gc -dry-run` 观察增长，再执行 `svnadmin gc`；
- 变更窗口：`svnadmin gc --compact=false` 可只做回收不做合并。
