# svngod 配置与多实例部署

> 配套文档 | 归属：《Go-SVN服务器架构设计方案》第 9 章 | 版本 v1.0 | 2026-11-02
>
> 本文所有 JSON 均已在 RustFS 1.0.4 + 本地盘环境实测：四库混布、两个 svngod 实例共享存储、3 节点 `quorum:2` 故障注入。

---

## 1. 启动方式

```bash
# 单库、flag 模式
svngod --addr 127.0.0.1:8080 --base-path /svn --repo-root /srv/svngod \
  --passwd /etc/svngod/passwd --authz /etc/svngod/authz

# 多库 / 多后端 / 多实例（推荐）
svngod --config /etc/svngod/svngod.json
```

flag 模式下仓库 `demo` 的访问 URL 为 `http://127.0.0.1:8080/svn/demo`（`addr` + `base-path` + 目录名）。

- `addr`：监听地址；多实例时每个实例不同（如 `:8080`、`:8081`，或不同主机）。
- `base-path`：URL 前缀；LB 后面的所有实例必须一致，否则客户端 URL 与重定向会错。
- 配置文件是严格 JSON（不支持注释）。

## 2. 顶层字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `addr` | string | 是 | 监听地址，如 `127.0.0.1:8080` 或 `0.0.0.0:8080` |
| `base-path` | string | 否 | URL 前缀，默认 `""`；示例统一用 `/svn` |
| `hooks` | string | 否 | hook 脚本目录（`pre-commit`/`post-commit`/`pre-revprop-change`） |
| `tls-cert` / `tls-key` | string | 否 | 同时设置时该实例直接提供 HTTPS；否则由 LB 终止 TLS |
| `max-uploads` | int | 否 | 全实例并发上传上限（0 = 默认 16） |
| `max-user-uploads` | int | 否 | 单用户并发上传上限（0 = 默认） |
| `commit-batch` | int | 否 | **仅命令行**：在线提交组提交批大小（0/1 = 关闭，默认 16） |
| `commit-window-ms` | int | 否 | **仅命令行**：组提交等待窗口毫秒数（默认 2） |
| `disable-metrics` | bool | 否 | 关闭 `/_metrics`（默认开启） |
| `admin-addr` | string | 否 | 管理 API 监听地址（空 = 关闭；建议回环/内网） |
| `admin-token` / `admin-token-file` | string | 否 | 管理 API Bearer Token（推荐 0600 文件或 `SVNGOD_ADMIN_TOKEN`） |
| `admin-allow-cidr` | string | 否 | 允许来源 CIDR，默认 `127.0.0.1/32,::1/128` |
| `repos` | array | 是 | 仓库列表，见第 3 节 |

## 3. 仓库与存储字段

```json
{
  "name": "demo",
  "storage": { "type": "file", "root": "/srv/svngod" },
  "authz": "/etc/svngod/authz-demo",
  "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd-demo" } ]
}
```

| 字段 | 说明 |
|---|---|
| `name` | 仓库名，URL 为 `<base-path>/<name>`；必须与建仓时的目录名/前缀最后一段一致。示例 `name=demo`、`base-path=/svn` → `http://<host>:<port>/svn/demo` |
| `authz` | SVN authz 文件路径；省略表示不鉴权（仍需认证） |
| `auth` | 认证链，按顺序尝试；至少一个 |

`storage` 支持三种类型：

| `type` | 必填字段 | 说明 |
|---|---|---|
| `file` | `root` | 本地目录；对象位于 `<root>/<prefix>/<name>/`，`prefix` 默认 `repos`（`file` 忽略自定义 prefix） |
| `s3` | `endpoint`,`access-key`,`secret-key`,`bucket`；可选 `prefix`、`ssl` | S3/RustFS/MinIO/AWS；`endpoint` 只写 `host:port`，不要带 `http://`；`prefix` 默认 `repos` |
| `mirror` | `mirrors`（≥2）；可选 `prefix`、`quorum` | 主备镜像；`prefix` 默认 `repos`；`quorum` 省略=可用性模式，≥2=严格模式 |

`mirror.mirrors[]` 的每一项与 `file`/`s3` 字段相同；主节点是列表第一项。**读路径**在主节点故障时自动切到下一健康节点；**写路径**（提交、修订发布、提交租约）在两节点主备下要求第一项（仲裁者）在线，仲裁者不可达时返回 `503` 且 `HEAD` 不变，绝不会只写一份就确认。3 节点及以上改用多数派仲裁，可容忍 1 个节点故障继续提交。

认证后端：

| `type` | 字段 |
|---|---|
| `local` | `passwd`：`user:password` 文件，支持 `{SHA}` / `{CRYPT}` |
| `ldap` | `url`、`starttls`、`base-dn`、`filter`、`bind-dn`、`bind-password`、`direct-bind-dn` |

### 3.1 URL 规则（配置到访问地址的映射）

最终 SVN URL 只由三件事决定，**与 `storage.type`、`prefix`、`quorum`、镜像拓扑无关**：

```
URL = <scheme>://<host>:<port><base-path>/<repos[].name>
```

- `scheme`：`http`；实例配置 `tls-cert`/`tls-key` 或 LB 终止 TLS 时为 `https`。
- `host:port`：实例的 `addr`；多实例部署时通常写 LB 的地址。
- `base-path`：顶层字段；为空时 URL 形如 `http://host:port/<name>`。
- `name`：`repos[].name`。`storage.prefix`（如 `multi-ha`）只是对象键前缀，不出现在 URL 里。

```bash
# 以第 4 节配置为例（addr=127.0.0.1:18400，base-path=/svn）
svn co  http://127.0.0.1:18400/svn/local-repo/trunk
svn co  http://127.0.0.1:18400/svn/s3-repo/trunk
svn co  http://127.0.0.1:18400/svn/hybrid-repo/trunk
svn co  http://127.0.0.1:18400/svn/ha-repo/trunk
```

| 配置形态 | 示例 URL |
|---|---|
| 本地盘 `file` | `http://127.0.0.1:18400/svn/local-repo` |
| 单 S3 `s3` | `http://127.0.0.1:18400/svn/s3-repo` |
| 本地+S3 `mirror` | `http://127.0.0.1:18400/svn/hybrid-repo` |
| 3 节点 `quorum:2` | `http://127.0.0.1:18400/svn/ha-repo` |
| `base-path` 为空 | `http://127.0.0.1:8080/<name>` |
| 实例直连 TLS | `https://svn.example.com:8443/svn/secure` |
| LB 终止 TLS | `https://svn.example.com/svn/assets` |

## 4. 单实例、多库混布（实测配置）

四个仓库分别使用：本地盘、单 S3、本地+S3 镜像、3 节点严格法定人数镜像。

```json
{
  "addr": "127.0.0.1:18400",
  "base-path": "/svn",
  "hooks": "/etc/svngod/hooks",
  "repos": [
    {
      "name": "local-repo",
      "storage": { "type": "file", "root": "/srv/svngod/local" },
      "authz": "/etc/svngod/authz",
      "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd" } ]
    },
    {
      "name": "s3-repo",
      "storage": {
        "type": "s3",
        "endpoint": "10.0.0.11:9000",
        "access-key": "svngod",
        "secret-key": "change-me",
        "bucket": "svn",
        "prefix": "multi"
      },
      "authz": "/etc/svngod/authz",
      "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd" } ]
    },
    {
      "name": "hybrid-repo",
      "storage": {
        "type": "mirror",
        "prefix": "multi-mirror",
        "mirrors": [
          { "type": "file", "root": "/srv/svngod/hybrid" },
          { "type": "s3", "endpoint": "10.0.0.11:9000",
            "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" }
        ]
      },
      "authz": "/etc/svngod/authz",
      "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd" } ]
    },
    {
      "name": "ha-repo",
      "storage": {
        "type": "mirror",
        "prefix": "multi-ha",
        "quorum": 2,
        "mirrors": [
          { "type": "s3", "endpoint": "10.0.0.11:9000", "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" },
          { "type": "s3", "endpoint": "10.0.0.12:9000", "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" },
          { "type": "s3", "endpoint": "10.0.0.13:9000", "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" }
        ]
      },
      "authz": "/etc/svngod/authz",
      "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd" } ]
    }
  ]
}
```

实测结果（RustFS 1.0.4）：

- 四个仓库均可被另一个实例（不同 `addr`）读取与提交，HEAD 同步。
- 本地盘 `verify`、S3 单后端 `verify`、镜像本地+S3 `verify`、三节点独立 `verify` 全部干净。
- `ha-repo`：3 节点中 1 个宕机仍可提交（约 9s，首次探测降级；之后 1s）；2 个宕机返回 503 且 HEAD 不变；恢复后无重复修订。

**访问 URL**（实例 `127.0.0.1:18400`，`base-path=/svn`）：

| 仓库 | URL |
|---|---|
| local-repo | `http://127.0.0.1:18400/svn/local-repo` |
| s3-repo | `http://127.0.0.1:18400/svn/s3-repo` |
| hybrid-repo | `http://127.0.0.1:18400/svn/hybrid-repo` |
| ha-repo | `http://127.0.0.1:18400/svn/ha-repo` |

```bash
svn ls  http://127.0.0.1:18400/svn/ha-repo/trunk
svn import ./assets http://127.0.0.1:18400/svn/hybrid-repo/trunk -m "release"
```

## 5. 建仓命令（必须与配置前缀一致）

`prefix` 决定对象在存储中的键前缀；**建仓与配置必须完全一致**，否则服务会打开空仓库或 repair 扫错前缀。

```bash
# 1) 本地盘：root 的上一级是配置里的 root，目录名 = repo name
svnadmin create /srv/svngod/local/local-repo

# 2) 单 S3：prefix=multi，repo name=s3-repo → 键 multi/s3-repo/...
svnadmin create --endpoint 10.0.0.11:9000 \
  --access-key svngod --secret-key change-me --bucket svn --prefix multi \
  /srv/svngod/meta/s3-repo

# 3) 本地+S3 镜像（对象形式，prefix=multi-mirror）
cat > /tmp/hybrid-mirror.json <<'JSON'
{"prefix":"multi-mirror","mirrors":[
  {"type":"file","root":"/srv/svngod/hybrid"},
  {"type":"s3","endpoint":"10.0.0.11:9000","access":"svngod","secret":"change-me","bucket":"svn"}]}
JSON
svnadmin create --mirror-file /tmp/hybrid-mirror.json /srv/svngod/hybrid/hybrid-repo

# 4) 3 节点严格法定人数（prefix=multi-ha，quorum=2）
cat > /tmp/ha-mirror.json <<'JSON'
{"prefix":"multi-ha","quorum":2,"mirrors":[
  {"type":"s3","endpoint":"10.0.0.11:9000","access":"svngod","secret":"change-me","bucket":"svn"},
  {"type":"s3","endpoint":"10.0.0.12:9000","access":"svngod","secret":"change-me","bucket":"svn"},
  {"type":"s3","endpoint":"10.0.0.13:9000","access":"svngod","secret":"change-me","bucket":"svn"}]}
JSON
svnadmin create --mirror-file /tmp/ha-mirror.json /srv/svngod/meta/ha-repo
```

建仓完成后，URL 只取决于配置的 `base-path` 与 `repos[].name`（与 `--prefix`/mirror-file 的 `prefix` 无关）。以上四条建仓命令对应的 URL：

```text
http://<host>:<port>/<base-path>/local-repo
http://<host>:<port>/<base-path>/s3-repo
http://<host>:<port>/<base-path>/hybrid-repo
http://<host>:<port>/<base-path>/ha-repo
```

`--mirror-file` 也接受**数组**形式（等价于 `prefix:"repos"`、`quorum:0`）：

```json
[{"type":"s3","endpoint":"10.0.0.11:9000","access":"k","secret":"s","bucket":"svn"},
 {"type":"s3","endpoint":"10.0.0.12:9000","access":"k","secret":"s","bucket":"svn"}]
```

## 6. 多 svngod 实例

多个实例是**无状态**的：它们只共享 `storage` 指向的后端；提交由跨进程租约 + WAL 串行化，因此不需要会话粘滞（LB 可轮询）。实例配置文件只有 `addr` 不同。

### 6.1 主备 S3（跨主机推荐）

两台主机各跑一个实例，后端是同一组 S3/RustFS：

```json
{
  "addr": "0.0.0.0:8080",
  "base-path": "/svn",
  "hooks": "/etc/svngod/hooks",
  "repos": [
    {
      "name": "assets",
      "storage": {
        "type": "mirror",
        "mirrors": [
          { "type": "s3", "endpoint": "10.0.0.11:9000", "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" },
          { "type": "s3", "endpoint": "10.0.0.12:9000", "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" }
        ]
      },
      "authz": "/etc/svngod/authz",
      "auth": [ { "type": "local", "passwd": "/etc/svngod/passwd" } ]
    }
  ]
}
```

第二台实例只把 `addr` 改成 `0.0.0.0:8081`（或同一 `:8080`，不同主机）。

**访问 URL**（仓库名 `assets`，`base-path=/svn`）：

- 经 LB：`https://svn.example.com/svn/assets`
- 直连实例 1：`http://10.0.0.21:8080/svn/assets`
- 直连实例 2：`http://10.0.0.22:8080/svn/assets`
- trunk：`https://svn.example.com/svn/assets/trunk`

```bash
svn co https://svn.example.com/svn/assets/trunk
```

nginx 参考：

```nginx
upstream svngod {
    least_conn;
    server 10.0.0.21:8080 max_fails=3 fail_timeout=5s;
    server 10.0.0.22:8080 max_fails=3 fail_timeout=5s;
    keepalive 64;
}
server {
    listen 80;
    client_max_body_size 0;
    proxy_request_buffering off;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    location /svn/ {
        proxy_pass http://svngod;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

- 大文件/万级文件提交必须关闭请求缓冲并放宽超时（`proxy_request_buffering off`、3600s）。
- 存储节点不足法定人数或正在恢复时，服务端返回 `503 + Retry-After`；客户端可重试，不会得到“半提交”。
- 2 节点镜像配 `quorum:2` 没有容错（任一节点故障即 503）；需要 RPO=0 + 容忍 1 节点故障请用 3 节点 `quorum:2`。

**两节点主备的故障语义（默认可用性模式，不配 `quorum`）**

| 故障 | 读 | 提交 |
|---|---|---|
| 第二项（备）S3 宕机 | 正常（主节点可服务） | 正常；写入只落主节点，备节点恢复后自动补齐 |
| 第一项（主/仲裁者）S3 宕机 | 正常（读自动切到备节点，返回最后已提交内容） | `503 + Retry-After`，`HEAD` 不变；恢复后重试成功 |

第一项是提交仲裁者：这样两个 svngod 进程（甚至配置顺序不同的进程）不会各自在一份副本上提交同一个修订号。代价是它宕机时整个仓库只读。若要求“主节点故障仍可提交”，使用 3 节点 `quorum:2`（容忍 1 节点故障且不丢已确认修订）。

备节点长期离线时，提交继续落在主节点（**单副本窗口**）：原子性/持久性仍由主节点的租约、WAL 与 HEAD CAS 保证，但主节点若在此时故障，离线期间的修订没有第二份。备节点恢复后执行：

```bash
svnadmin repair --mirror-file mirror.json <repo>   # 同步补齐缺失的 pack/对象与 HEAD
svnadmin replicas --mirror-file mirror.json <repo> # 逐成员 HEAD/UUID/索引摘要，任何差异退出码 1
svnadmin replicas -verify --mirror-file mirror.json <repo>  # 再对每个成员跑一遍全量 verify
svnadmin replicas -verify -textfile /var/lib/node_exporter/textfile/repl.prom --mirror-file mirror.json <repo>  # Prometheus 指标
```

`repair` 只列举 `revs/`、活动分片的 `revs-loose/`、`revprops*/`、`texts/`、`chunks/`、`dirs/` 与 `current` 等控制键；`journal/` 与提交租约键不参与复制（前者一条/修订、后者是仲裁者独有），因此千万级仓库的修复不会被对象数量拖垮。

### 6.2 本地盘 + S3 镜像（同机多实例 / 共享文件系统）

`file` 后端是进程可见的本地路径。多个实例共享同一镜像时，**必须能访问同一个本地目录**（同机多端口，或 NFS/共享盘挂到相同路径）；跨主机各自本地盘无法互为镜像，请改用 S3 单后端或 S3 主备。

同机两个实例（`addr` 分别为 `127.0.0.1:18400` / `:18401`）共用：

```json
{
  "name": "hybrid-repo",
  "storage": {
    "type": "mirror",
    "prefix": "multi-mirror",
    "mirrors": [
      { "type": "file", "root": "/srv/svngod/hybrid" },
      { "type": "s3", "endpoint": "10.0.0.11:9000",
        "access-key": "svngod", "secret-key": "change-me", "bucket": "svn" }
    ]
  }
}
```

- 本地 `root` 必须是所有实例相同的绝对路径。
- 本地盘故障（权限/挂载丢失）时自动走 S3；恢复后 repair 按仓库前缀补齐。
- 本地盘是单点：同机多实例只解决进程故障，不解决主机故障；跨主机容灾仍建议 S3 主备。

**访问 URL**（两个实例等价，指向同一逻辑仓库）：

- `http://127.0.0.1:18400/svn/hybrid-repo`
- `http://127.0.0.1:18401/svn/hybrid-repo`
- 经 LB：`http://svn.internal/svn/hybrid-repo`

```bash
svn co http://127.0.0.1:18401/svn/hybrid-repo/trunk
```

### 6.3 严格法定人数（RPO=0）

```json
"storage": {
  "type": "mirror",
  "quorum": 2,
  "mirrors": [
    { "type": "s3", "endpoint": "10.0.0.11:9000", "access-key": "k", "secret-key": "s", "bucket": "svn" },
    { "type": "s3", "endpoint": "10.0.0.12:9000", "access-key": "k", "secret-key": "s", "bucket": "svn" },
    { "type": "s3", "endpoint": "10.0.0.13:9000", "access-key": "k", "secret-key": "s", "bucket": "svn" }
  ]
}
```

| 节点数 | `quorum` | 容忍故障 | 说明 |
|---|---|---|---|
| 3 | 2 | 1 | 推荐：RPO=0 且保留可用性 |
| 3 | 3 | 0 | 全写才确认，最严格 |
| 2 | 2 | 0 | 无容错；任一节点故障即 503 |
| 任意 | 省略/1 | 单点 | 可用性优先；最后一次提交可能只在一份副本 |

**访问 URL**：与普通镜像完全一致，`quorum` 只影响写入确认，不改变 URL。

- 直连：`http://10.0.0.21:8080/svn/ha-repo`
- 经 LB：`https://svn.example.com/svn/ha-repo`
- trunk：`https://svn.example.com/svn/ha-repo/trunk`


### 6.4 提交吞吐调优与规模压测

单次提交在 S3 主备上约 220–280ms（租约 12–34ms、revblock+revprops 47–78ms、WAL 32–36ms、HEAD CAS 65–95ms），单仓库约 4 次/秒。提高吞吐的两条路径：

- **在线组提交（默认开启）**：`-commit-batch 16 -commit-window-ms 2` 把并发到达的 DAV 提交合并为一次租约与一次 HEAD CAS。原生 svn 客户端仍受 MKACTIVITY/PUT/MERGE 会话往返限制，8 并发约 4.5 次/秒（关闭时 3.9）。
- **批量写入**：`Repo.CommitBatch`（`cmd/revscale`、批量导入）一次构建多个修订，revblock/revprops/WAL 并发写，整批一次 CAS。实测 K=64 单进程约 33 次/秒；8 个仓库并发 45–49 次/秒；16 个并发会因后端小对象写饱和降到约 29 次/秒，因此规模压测用 8 个 worker。

千万级长跑（16 仓 × 625,000 修订）：

```bash
revscale -store mirror -endpoints 10.0.0.11:9000,10.0.0.12:9000 \
  -ak K -sk S -repo scale00 -batch 64 -idxbase 1000000 -target 625000
```

- 每个进程用不重叠的 `-idxbase`（每次启动一个 100 万块），续跑不会撞路径。
- 每约 6 小时对两个副本做一次 `svnadmin verify --all-revs`；长跑结束后 `svnadmin gc` 回收 loose 对象并裁剪 journal。
- 备节点故障期间提交继续（单副本），恢复后先 `svnadmin repair` 再续跑。
- 副本漂移检查：`svnadmin replicas` 分别读取每个成员的 `head`、`uuid` 与**副本摘要**（格式参数 + 所有 `segs/<shard>.idx` 的 first/count/sha + 所有属性覆盖列表及其内容哈希）。任一不一致即打印 `DRIFT` 并返回 1，可直接接监控；`-verify` 逐成员全量校验（能发现“HEAD/索引一致但段对象缺失”），`-repair` 先跑一遍镜像 repair 再比较。
  指标：`svngod_replica_head{repo,member}`、`svngod_replica_verify_issues{repo,member}`（-1 = verify 失败）、`svngod_replica_consistent{repo}`；textfile 原子写入（tmp+rename），可直接被 node_exporter textfile collector 采集。
  摘要不一致时会逐键列出差异：缺失对象标明是哪一侧缺，大小不同直接给出字节数，索引与属性覆盖对象在大小相同的情况下再比对内容哈希（`content differs [hashA hashB]`）；段对象只比大小（逐段下载内容代价过高，正确性由 `-verify` 覆盖）。
  `-repair` 的收敛方式：先跑镜像 repair 补齐缺失对象，再让**每个成员用自己的不可变段重建索引**（不做跨成员复制，避免故障切换后把陈旧映射传播到另一侧），并清理该死属性覆盖；随后重新比较摘要。
  实测：健康双副本一致；删掉一个成员的 `segs/0000000000.idx` → 摘要改变；删掉一个 `seg-revprops` 覆盖对象 → 摘要改变且 `-verify` 报 `revision 2 property override is missing`；删掉一个 `.seg` 对象 → `-verify` 报 `rev=1 store: object not found`。两种破坏都能被 `replicas -repair` 从另一成员补齐，随后摘要与 verify 恢复一致。


管理 API 的启用、接口与热加载语义见 [`管理API与热加载.md`](管理API与热加载.md)。

### 6.5 删除仓库

```bash
# 彻底删除（控制键、分片、loose、journal；按已知键范围并发删除）
svnadmin delete-repo -force --workers 8 --batch 100 \
  --endpoint 10.0.0.11:9000 --access-key K --secret-key S --bucket svn --prefix repos <repo>

# 只删控制键：仓库立即从 svn 服务消失，剩余对象留给离线清理
svnadmin delete-repo -force -control-only ... <repo>
```

- 删除前可加 `--dry-run` 只统计对象数；`--head N` 用于元数据已删除、需要重跑残留清理的仓库。
- RustFS 实测：单批 1000 键删除在长时间大流量下可能挂起（客户端无超时），工具已为每批加 90s 超时与重试；**100 键小批量更稳定**（约 1 万键/秒），大批量或高并发会互相饿死。
- 删除只作用于 `--endpoint` 指定的副本；主备场景需对两个副本分别执行（备节点离线时其残留无法清理）。
- 仓库数据删除不可恢复；生产环境先 `--dry-run` 确认，并确认没有客户端仍指向该 URL。

## 7. 认证、TLS 与 hooks

```json
{
  "addr": "0.0.0.0:8443",
  "base-path": "/svn",
  "hooks": "/etc/svngod/hooks",
  "tls-cert": "/etc/svngod/tls/server.crt",
  "tls-key": "/etc/svngod/tls/server.key",
  "repos": [
    {
      "name": "secure",
      "storage": { "type": "file", "root": "/srv/svngod" },
      "authz": "/etc/svngod/authz",
      "auth": [
        {
          "type": "ldap",
          "url": "ldap://ldap.example.com:389",
          "base-dn": "ou=people,dc=example,dc=com",
          "filter": "(uid={{username}})",
          "bind-dn": "cn=svngod,ou=services,dc=example,dc=com",
          "bind-password": "change-me"
        },
        { "type": "local", "passwd": "/etc/svngod/passwd" }
      ]
    }
  ]
}
```

- `auth` 按顺序尝试，任一成功即通过；LDAP 两种模式：`bind-dn`+`filter`（search+bind）或 `direct-bind-dn`（`uid={{username}},...`）。
- hooks 目录内脚本需可执行；`pre-revprop-change` 不存在时 revprop 修改返回 403（与 mod_dav_svn 一致）。
- `tls-cert`/`tls-key` 同时设置时实例直接 HTTPS；证书也可由 LB 终止。

**访问 URL**（仓库 `secure`，`base-path=/svn`）：

- 实例直连 TLS：`https://svn.example.com:8443/svn/secure`
- LB 终止 TLS：`https://svn.example.com/svn/secure`

```bash
svn co --username alice https://svn.example.com:8443/svn/secure/trunk
```

### 7.1 Apache `mod_authnz_ldap` 配置迁移

给定 Apache 配置：

```apache
AuthBasicProvider ldap
AuthLDAPURL "ldap://ldap.example.com:389/ou=people,dc=example,dc=com?cn"
```

字段对应关系：

| Apache | svngod JSON | 说明 |
|---|---|---|
| `AuthBasicProvider ldap` | `"auth": [ { "type": "ldap", ... } ]` | 仍是 HTTP Basic |
| `ldap://ldap.example.com:389` | `"url": "ldap://ldap.example.com:389"` | `ldaps://` 或 `starttls: true` 用于 TLS |
| `/ou=people,dc=example,dc=com` | `"base-dn": "ou=people,dc=example,dc=com"` | 搜索基准 |
| `?cn` | `"filter": "(cn={{username}})"` | 属性 → 过滤器；`{{username}}` 会被转义 |
| 无 `AuthLDAPBindDN` | 不配 `bind-dn` | 匿名搜索；该服务器实测允许匿名搜索 |
| `AuthLDAPBindDN` / `AuthLDAPBindPassword` | `bind-dn` / `bind-password` | 匿名搜索被禁用时使用服务账号 |

对应的最小仓库配置：

```json
{
  "addr": "0.0.0.0:8080",
  "base-path": "/svn",
  "repos": [
    {
      "name": "ldap-repo",
      "storage": { "type": "file", "root": "/srv/svngod" },
      "authz": "/etc/svngod/authz",
      "auth": [
        {
          "type": "ldap",
          "url": "ldap://ldap.example.com:389",
          "base-dn": "ou=people,dc=example,dc=com",
          "filter": "(cn={{username}})"
        }
      ]
    }
  ]
}
```

**访问 URL**：`http://<svngod-host>:8080/svn/ldap-repo`。例如在本机测试配置（`addr=127.0.0.1:18500`）下：

```bash
svn co --username <cn> http://127.0.0.1:18500/svn/ldap-repo/trunk
curl -u <cn>:<password> -X PROPFIND -H 'Depth: 0' \
  http://127.0.0.1:18500/svn/ldap-repo/
```

如果匿名搜索不可用，加服务账号：

```json
{
  "type": "ldap",
  "url": "ldap://ldap.example.com:389",
  "base-dn": "ou=people,dc=example,dc=com",
  "filter": "(cn={{username}})",
  "bind-dn": "cn=svngod,ou=services,dc=example,dc=com",
  "bind-password": "change-me"
}
```

如果用户 DN 规则固定（无需搜索），可直接绑定：

```json
{
  "type": "ldap",
  "url": "ldap://ldap.example.com:389",
  "direct-bind-dn": "cn={{username}},ou=people,dc=example,dc=com"
}
```

注意事项：

- svngod 在 `base-dn` 下做**整棵子树**搜索，并要求恰好 1 条匹配；Apache 的默认 scope 可能是 `one`，若目录中存在同名用户，请加更精确的 filter（如 `(&(cn={{username}})(objectClass=person))`）或使用 `direct-bind-dn`。
- svngod 的 LDAP 只负责**认证**；Apache 的 `Require ldap-group` / `AuthLDAPGroupAttribute` 这类基于 LDAP 组的授权需改写为 SVN authz 文件（`authz`）。
- `auth` 是链式尝试：LDAP 在前、本地密码表在后时，LDAP 故障不会阻断本地账号；但 LDAP 配错（base/filter）会让 LDAP 用户全部 401。
- 认证仅在 authz 拒绝匿名时强制。若 authz 配成 `* = rw`，匿名请求会直接成功（实测无凭据 PROPFIND 返回 207）；带凭据时仍会走 LDAP（错误凭据返回 401）。

该服务器实测（2026-11）：TCP 可达；匿名搜索 `(cn=test)` 返回 0 条、无权限错误；配置映射后用 `-u test:bad` 请求返回 401（约 10ms），说明搜索+绑定链路已生效。真实账号能否 200 需要有效凭据验证。

## 8. 可观测性与健康检查

- `GET /_metrics`：Prometheus 指标，含每仓库的 mirror 健康、主节点、上传限流等。默认不鉴权，建议只在内网/LB 访问。
  - 示例：`http://127.0.0.1:18400/_metrics`
- 就绪检查：`OPTIONS /svn/<repo>/` 返回 200/207 且未返回 503 即可用；存储全不可用时返回 503。
  - 示例：`OPTIONS http://127.0.0.1:18400/svn/local-repo/`
- 日志：启动行含 `listening on ...`；提交/修复/前滚均有明确日志（`journal: rolled forward revision N`、`mirror[i] ...`）。

systemd 参考：

```ini
[Unit]
Description=svngod SVN server
After=network-online.target

[Service]
ExecStart=/usr/local/bin/svngod --config /etc/svngod/svngod.json
Restart=always
RestartSec=2
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target
```

## 10. 常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动即 500/503，日志 `dial tcp ... connection refused` | `endpoint` 写成了 URL 或节点未启动 | 只写 `host:port`；确认 RustFS/MinIO 监听 |
| 仓库 404 / 空库 | 配置 `prefix` 与建仓 `--prefix`/mirror-file `prefix` 不一致 | 二者必须完全一致（默认都是 `repos`） |
| repair 报“补齐了”但节点仍缺对象 | 旧版本 prefix 未传给 MirrorStore（已修复）；确认使用最新版本 | 升级；日志可用 `SVNGOD_DEBUG_REPAIR=1` 查看 `sets/keys/missing` |
| 两节点镜像任一节点宕机就 503 | 配了 `quorum:2` 但只有 2 个节点 | 去掉 `quorum`（可用性）或加到 3 节点 |
| 两节点可用性模式，主 S3（列表第一项）宕机后提交 503、读正常 | 第一项是提交仲裁者，防止多进程各写一份副本 | 安全设计；需要主节点故障仍可提交请用 3 节点 `quorum:2` |
| 批量导入或进程被强杀后，备 S3 `svnadmin verify` 报 `object not found` | 备节点写入失败时只记在进程内存的 pending 增量里，写入进程已退出 | `svnadmin repair --mirror-file FILE <repo>` 同步扫描并补齐；正常运行中的 svngod 会自动修复 |
| 多实例各自本地盘，数据不一致 | `file` 后端不共享 | 改为 S3 单后端/主备，或把本地目录做成共享挂载 |
| 大文件提交 413/超时 | LB 缓冲或超时太小 | `proxy_request_buffering off`、`client_max_body_size 0`、3600s |
| revprop 修改 403 | 未安装 `pre-revprop-change` hook | 放入 hooks 目录并 chmod +x |
| LDAP 正确密码仍 401 | `base-dn`/`filter` 不匹配，或匿名搜索被禁用 | 用 `ldapsearch` 验证 `(cn=user)`；加 `bind-dn`/`bind-password` 或改 `direct-bind-dn` |
| LDAP 登录成功但 403 | authz 文件未授权该用户/组 | LDAP 组授权需写入 authz；svngod 不做 LDAP 组解析 |
