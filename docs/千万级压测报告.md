# 千万级修订压测报告（2026-11）

> 目标：在 4 个 svngod 进程 + 主备 RustFS 的拓扑上写入 **10,000,000 个修订**，验证组提交吞吐、提交原子性与数据完整性，并观察长跑中的规模化瓶颈。

## 1. 环境与参数

| 项 | 配置 |
|---|---|
| 服务端 | 4 × svngod（18600–18603），多库配置，主备 S3 镜像 |
| 主 S3 | RustFS `192.168.23.228:9000`，bucket `svn-ext`，prefix `repos` |
| 备 S3 | RustFS `192.168.23.245:9000`（**11-05 起故障，未恢复**） |
| 仓库 | 16 个（`scale00`–`scale15`），每仓 625,000 修订 |
| 写入方式 | `cmd/revscale`，fs 层 `CommitTxn`/`CommitBatch`，8 个 worker |
| 组提交 | K=64，每次批量一次租约、一次 HEAD CAS |
| 路径分片 | 六层十进制（每层 ≤10 子节点），每次提交只重写约 7 个小目录节点 |
| 用户 | 8 个作者身份轮换 |

### 3.1 规模化瓶颈：写延迟随对象数上升

| 指标 | 早期 | 末期 |
|---|---|---|
| 1KiB 单对象 Put（主副本） | 25–31ms | **约 860ms** |
| 同对象 Get | 约 1ms | 约 1ms |
| 单 worker 吞吐 | 6.3 次/秒 | 3.7–4.3 次/秒 |

- 读路径不受影响，HTTP 往返仍约 5ms；**只有写路径劣化**，说明瓶颈在 RustFS 的写路径。
- **压测停止后复测**：同一 1KiB Put 回落到约 **27ms**。因此 860ms 主要是持续 8 worker 批量提交造成的写队列/刷盘压力，对象规模会放大它，但闲置时并不会持续劣化。
- 长跑期间未做 GC：每个修订一条 `journal/<N>`（共 1000 万条），且已打包分片的 loose rev/revprops 仍保留（每仓约 125 万个小对象），主副本对象总数达到数千万；这是收尾 GC 的主要工作量。
- **删除吞吐实测**：RustFS 单批 1000 键删除约 **26–29 秒**（约 36 键/秒）。因此千万级数据的全量 GC 是数小时到数天级别的后台任务；`TrimJournal` 已从“列 62 万键再删”改为**按精确键范围并发删除**，避免在大仓库上做慢速 list。

## 4. 完整性与原子性

- **最终验收**：16 仓 `svnadmin verify --all-revs --from 1` 全部 `rc=0`、`no integrity issues`（1..625,000）。
- **运行中 checkpoint**：每约 6 小时轮换仓库做全量校验，`scale00/04/08/12` 等在 625k 处均通过。
- **单副本窗口**：备 S3 于 11-05 起不可达，提交继续落在主副本；提交租约、WAL、单次 HEAD CAS 不变，未出现半个修订或重复修订号。
- **慢写期错误**：worker 日志中的 `arbiter unavailable: Put .../current: context deadline exceeded` 是批 CAS 超时；该批次未发布、HEAD 不变，worker 继续，属可重试失败。
- **失败批次**：批内任一写失败或 CAS 失败时整批不发布；客户端未收到成功即不会把该修订计入 `done`。

## 5. 故障与修复（长跑中暴露）

| 问题 | 修复 |
|---|---|
| 备节点落后 2 万修订且 repair 无法恢复 | repair 列举改为精确控制键、S3 前缀保留尾部斜杠、loose 只列活动分片、可达性探测读 `current` |
| 列表后被删除的瞬时对象把备节点标记失败 | 复制时容忍 `NotFound`；提交租约键不进入 repair 范围 |
| 打包后的 loose 清理以批量 DELETE 镜像到备节点，8 秒超时反复踢备 | 清理移出提交路径，留给 `svnadmin gc`；repair 列表不受 loose 垃圾影响 |
| 续跑路径索引与修订号错位 | `-idxbase` 每次启动分配独立的 100 万索引块 |
| 租约校验与心跳 CAS 竞争 | `Verify` 改为只读，心跳唯一续约者 |

## 6. 收尾

1. **全量校验**：已完成（16/16）。
2. **GC（主副本）**：逐仓执行 `svnadmin gc --endpoint <primary> --keep-journal 4096 <repo>`，回收已打包分片的 loose rev/revprops，并裁剪 journal 至最近 4096 条。删除已改为 8 路并发；受 RustFS 删除/列举延迟影响，单仓仍需数十分钟，当前在后台顺序执行。
3. **备副本**：若 245 恢复，先 `svnadmin repair --mirror-file ... <repo>` 补齐 1000 万修订的第二副本，再对两个副本做全量校验；若不恢复，本轮以单副本交付。
4. **后续优化**：把一批修订合并进单个 segment 对象（一次写发布多个修订）；长跑中周期性 GC（每约 5 万修订）；评估本地 NVMe WAL + 异步 S3 的写路径。

## 7. 复现

```bash
# 单仓
revscale -store mirror -endpoints 10.0.0.11:9000,10.0.0.12:9000 \
  -ak K -sk S -repo scale00 -batch 64 -idxbase 1000000 -target 625000

# 16 仓 × 625k，8 个 worker，作者轮换
# 守护进程每 30 分钟记录进度、每约 6 小时轮换仓库校验
```
