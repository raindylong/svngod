# 数据安全与原子性审计清单

本文件是**可复用的审计方法**，不是一次性报告。每当改动提交路径、GC 路径或
副本读写路径时，按对应章节逐条过一遍。

判定标准只有一条：**宁可拒绝服务，不可静默破坏数据**。所有"读不到就当没有"、
"失败就跳过"的写法都是缺陷候选。

---

## 1. 删除路径（爆炸半径最大，先审）

`svnadmin gc` 是仓库里唯一主动删除数据的入口。每条 `Collect*` 支路都必须满足：

### 1.1 三条硬性规则

| # | 规则 | 反例（都是已修的真实缺陷） |
|---|---|---|
| 1 | 建立引用集时，**任何**读取失败都要向上传播 | `cdc.Parse` 失败静默跳过 → 该修订的 chunk 全部被当垃圾 |
| 2 | 必须区分"对象不存在"与"读取失败" | `loadSegmentIndex` 把 `ErrNotFound` 映射为空列表 → 索引丢失 = 整个 shard 被删 |
| 3 | 白名单必须**自校验覆盖范围** | keep-set 只看存在的条目，不校验是否覆盖到 HEAD |

### 1.2 检查方法

对每个 `Collect*` / `Compact*` 函数，搜这三个模式：

```bash
# 读失败被跳过（最可疑）
grep -n 'err != nil {' -A1 internal/fs/*.go | grep -B1 continue

# 错误被装饰成"无数据"
grep -n 'errors.Is(err, store.ErrNotFound)' -A2 internal/fs/*.go

# err == nil 里的静默分支
grep -n 'if .*; err == nil {' internal/fs/*.go
```

然后回答三个问题：

1. 读失败是否让整轮收集**拒绝执行**（而不是少删一点）？
2. "不存在"和"读失败"在返回值上是否可分？
3. 判断依据的白名单是否自身校验过完整性（如索引连续覆盖到 HEAD）？

### 1.3 当前状态

| 支路 | fail-closed 的判据 | 守护测试 |
|---|---|---|
| `CollectTexts`（chunk manifest） | `chunkScanOK=false` → 拒绝收集 chunk | `TestCollectTextsKeepsChunksOfCorruptManifest` |
| `CollectTexts`（dir 表） | `dirScanOK=false` → 跳过 dir 收集 | `TestCollectTextsSkipsDirsWhenTableUnreadable` |
| `CollectTxnData`（activity manifest） | 读失败直接返回错误 | `TestGCDeletionPathsRefuseOnReadFailure` |
| `CollectOrphanSegments`（keep set） | 要求索引连续覆盖到 HEAD | `TestSegmentKeepSetRefusesLostIndex` |
| `CollectLoose`（仅删已打包 shard） | 标记读不到 → 跳过该 shard | `TestCollectLooseSkipsWhenPackedMarkerUnreadable` |
| `CompactSegments`（合并即换索引） | 索引读失败 → 报错不合并 | `TestCompactSegmentsRefusesOnIndexReadFailure` |

至此六条支路都有守护测试，且**新增支路不会再漏**：`gc_meta_test.go` 里的
`TestEveryGCSweepHasAFailClosedCase` 用反射枚举 `*Repo` 上所有 `Collect*`/`Compact*`
方法，没有对应用例就直接失败。配套的 `TestGCSweepsFailClosedOnReadFailure` 把五族
扫掠各跑两遍（健康 / 注入读失败）。

断言的是**数据仍可读**，不是"键还在"。健康扫掠本来就该删东西，合并也会换掉段文件，
所以"这些键仍存在"是错的判据；每条用例改为重读仓库（每个修订、或整棵分页目录）
必须仍能解开——这才是"引用集不全"真正破坏的东西。

健康跑还断言删除数 ≥ 1：否则空转的夹具会让故障断言凭空成立。

注意 `CollectTexts` 的两个分支**失败行为不同**：

- chunk manifest 读不到 → `chunkScanOK=false` → **拒绝整轮收集**（返回错误）
- dir 表读不到 → `dirScanOK=false` → **跳过 dir 收集，但 texts/chunks 照常收集**，返回 nil

差异的理由是引用集独立：chunk manifest 坏了只影响 chunks，dir 表坏了只影响 dirs。
但这也意味着 **dir 表损坏时调用方从返回值上看不出"本轮没检查 dirs"**，只能从日志
`gc: cannot read dir table ...` 发现。运维上值得留意这条日志——它出现时 GC 并不完整。

### 写这类测试的两个坑（都踩过）

**1. 读缓存会绕过故障注入。** `isPacked` 只缓存正结果，`PackShard` 期间已经问过一次，
注入故障后 `isPacked` 直接命中缓存返回 `true`，根本不读被注入的标记。注入前必须
`r.cache.Clear()`。同理要检查被测路径上是否还有其它缓存层（`segDecoded`、`nodeCache`）。

**2. 打包会异步删 loose 副本。** `packShardLocked` 起一个 goroutine 回收 loose 对象
（打包后它们就是冗余的）。测试若在 `PackShard` 返回后立刻读计数，会和这个后台清理竞争，
表现为"数字随机变化、`CollectLoose` 报告删 0 但对象却少了"。必须等计数稳定
（本文件的 `waitLooseStable`）。这条在 macOS 上偶发通过、Linux 上稳定失败——**同一测试在
两个平台结果不同，通常说明它在依赖时序而非逻辑**。

### 有 test 和测得到是两回事

写守护测试最容易犯的错，是让断言在"什么都没发生"时也成立。这轮踩到的三种：

**夹具没进删除路径。** txn 夹具有个 `{"dataRef":"live123"}`，而代码的引用正则只收
十六进制（`[0-9a-f]+`），于是这条"存活证据"从第一天起就没被认出来——健康跑里它被
当孤儿删掉，故障跑断言"它还在"照样过。`baseline >= 1` + 健康跑后复查完整性才把它逼出来。

**断言了错的量。** 第一版断言"guard 前缀下的键一个不少"，健康跑立刻失败：扫掠的职责
就是删东西。换成"重读仓库仍可解"，才既放过该删的，又盯住不该删的。

**故障没生效。** 缓存层（`isPacked` 的正结果、dir 表解码）会把注入的读失败整个绕过，
测试于是在"无故障"状态下通过。凡是注入故障，先确认那条路径真的读了。

### 测试有效性怎么确认

这些测试的价值取决于**能否抓到真实的 fail-open 变体**，所以每条都做过反向验证：
把判据改成危险的默认值（例如 `CollectLoose` 把"标记不可读"当作"已打包"），测试必须失败。

已验证会失败的变体：
- `CollectLoose` 未知当作已打包 → `loose objects deleted while the packed marker
  was unreadable: 5 -> 0`（整 shard 的 loose 副本被删，而它当时是唯一副本）
- `CompactSegments` 把不可读索引当作空 → `compaction ran with an unreadable shard index`
- `CollectTexts` 的 dir 扫描忽略表读取失败 → `dir objects deleted from a partial
  reference set: 17 -> 1`（16 个目录桶被删，目录再也解不出来）
- `segmentKeepSet` 不校验覆盖范围 → 见 `TestSegmentKeepSetRefusesLostIndex`

### 两条删除支路的语义差异

`CollectLoose` 和 `CompactSegments` 的判据不同，别混淆：

- **`CollectLoose`** 删的是"已打包 shard 的 loose 副本"。安全性完全依赖
  `isPacked` 的正确性——若误判为已打包，删掉的是**唯一副本**。所以标记读不到时必须跳过，
  而不是猜。
- **`CompactSegments`** 先写合并对象、再 CAS 换索引、**最后延迟 60 秒删源段**。
  删除发生在索引已经指向新对象之后，所以中途失败只会留下孤儿（由
  `CollectOrphanSegments` 回收），不会丢数据。它的 fail-closed 点在"索引不可读时不合并"。

### 1.4 演练要求

- GC 前先 `gc -dry-run`，观察 `orphans` 数量。**异常突增通常意味着索引或 manifest 损坏，而不是真的产生垃圾**。
- `verify --all-revs` 报 `segment index ... ends at N, HEAD needs M` 时，先 `repair --rebuild-index`，再跑 GC。修复前 GC 会拒绝执行，这是预期行为，不是故障。

## 2. 提交路径（原子性核心）

### 2.1 必须保持的顺序

```
lease → reconcileJournal → readCurrentStrict → ensureNoPendingPublication
      → OCC 检查 → 写数据对象 → 写 WAL → HEAD CAS → lease.Release
```

关键不变量：

| 不变量 | 位置 | 违反后果 |
|---|---|---|
| 分配 `head+1` 前确认没有该修订的 WAL 记录 | `ensureNoPendingPublication` | 覆盖另一修订的数据（split-lease 类） |
| 数据对象先于 HEAD CAS 落盘 | `putBatchObjects` / `publishSegmentPlans` | ack 后数据不可达 |
| CAS 失败时用 `journalOwns` 判定归属 | `wal.go:walRecordMatches` | 误判他人提交为自己的 |
| delta 提交要求 HEAD 节点与客户端 diff 起点**同一** | `commitTxn` OCC | 静默覆盖他人的 delete/re-add |

### 2.2 `CommitBatch` 的部分成功语义（易误用）

默认情况下 `CommitBatch` 逐条应用，**中间被拒不影响前后条目**：

```
revs=[2 0 3]  errs=[nil "out of date" nil]  err=nil  head=3
```

即：**修订号会出现空洞**。这是刻意的——服务端提交队列靠它让 disjoint 路径并发合并，
改成整批失败会退化成交互式提交互相打架。

**批量导入不能接受空洞**：dump 的修订连续且父修订编号固定，缺一个号就无法续传，
只能重建。因此 `CommitBatch` 提供 `AllOrNothing()`：

| 模式 | 调用方 | 中间失败的行为 |
|---|---|---|
| 默认（逐条） | 服务端提交队列、svn 客户端 | 前后条目照常发布，`revs` 出现 0 |
| `AllOrNothing()` | `svnadmin load` | 整批不发布，`revs` 全 0，返回整批错误 |

### `AllOrNothing` 实际保证什么（重要，别误读）

承诺的是**"不留空洞"，不是"绝不发布任何东西"**。两种失败阶段要分开看：

| 失败阶段 | 是否写了对象 | 结果 |
|---|---|---|
| 树校验失败 / 修订构建失败 | 否（rev-block 与树都在内存） | 仓库完全未变，`revs` 全 0 |
| WAL 写入中途失败 | **是**（记录逐条落盘） | 已写入的连续前缀会被 replay 发布，`revs` 仍全 0 |
| HEAD CAS 失败 | 是（数据对象/WAL 已写） | 未发布；若 peer 的 replay 抢先发布了我们的记录，`revs` 保留（确实成功） |

第二行是**不可回滚的**：WAL 记录是持久对象，删它们可能删掉别人已 ack 的记录，风险远大于收益。
所以不去删，而是靠 replay 的严格连续性兜住——`replayJournal` 只从 `head+1` 逐条推进，
遇到缺失或 `Parent != head` 立即停止，**永远只发布连续前缀**。结果是一个更短的批，不是空洞。

因此 load 的失败信息不写"nothing published"，而是报出实际 head：

```
dump: batch abandoned, target head is 4 (no gap introduced): ...
```

第三行是唯一"报告全 0 但实际部分成功"的反面情形，所以 CAS 分支必须逐组判定
`segmentOwns`：只有确认是我们的且已发布，才保留 `revs`；否则清零并报错。

守护测试：
- `TestPartialWalIsRolledForwardByReplay` —— v1 路径 WAL 部分写入后 replay 只发布前缀
- `TestAllOrNothingBatchLeavesNoHoleAfterPartialWal` —— 无修复时 `revs[0]=2` 谎报成功
- `TestSegmentBatchCasFailureReportsNothingPublished` —— segmented 路径 CAS 失败必须全 0

### segmented 与 v1 的差异

segmented 仓库**没有部分 WAL 的窗口**：一批只写一条 `journal/<first>` 记录
（`writeSegmentJournalBatch`），单次 Put 要么全成要么全败。v1 是每修订一条，
才有上表第二行。这也是推荐用 `create --segments` 建仓的又一个理由。

`load` 使用该选项，失败信息形如：

```
dump: nothing published (target head stays 0): fs: batch abandoned before
publishing (request rejected at request 1): fs: delete of nonexistent path ...
```

守护测试：
- `TestCommitBatchPartialFailureIsVisible` —— 默认语义（空洞可见）
- `TestCommitBatchAllOrNothingLeavesNoGap` —— 整批不发布
- `TestCommitBatchDefaultStillPartial` —— 确认服务端语义未被改动
- `TestLoadRejectsConflictingDumpWithoutPublishing` —— 无该选项时 head 会前进到 1，
  有该选项时保持 0

### 2.3 检查方法

改动 `commitTxn` / `CommitBatch` 后，跑：

```bash
go test -run 'TestCommitAtomicityUnderWriteFailures|TestLargeBatchReplayBeyondWindow' -race ./internal/fs/
go test -run TestChaosMatrix ./internal/fs/
```

混沌矩阵（`chaos_matrix_test.go`）覆盖：提交中掉副本、两副本全掉、rev-block 撕裂写。
新增故障模式就往矩阵里加一行。

## 3. 副本与租约路径

### 3.1 `QuorumGet` 的返回值必须被检查

`QuorumGet` 返回 `(value, count, err)`，其中 `count` 是**读到相同值的副本数**。
它不会因为 count 不足而报错，调用方必须自己判：

```go
b, count, err := qr.QuorumGet(ctx, key)
if err != nil { ... }
if count < quorum { /* 不可信 */ }
```

已检查的调用点：`lease.go:readOwn`、`releaseCommitLeaseQuorum`、
`mirror_reconcile.go`、`mirror_repair.go`。

`readLease` 只要求 `count >= 1` 是**刻意**的：它只用于"租约是否已过期"的快速判断，
真正的保护是随后的 `DeleteIfMatchQuorum`（条件删除 + quorum 门槛）。
ETag 不匹配时删除失败，所以读到陈旧副本不会误删有效租约。

### 3.2 检查方法

```bash
grep -rn 'QuorumGet(' internal/ --include='*.go' | grep -v _test
```

对每个调用点确认：`count` 是否参与判断？不参与的地方，是否有等价的条件写（CAS /
DeleteIfMatch）兜底？

## 3.3 格式标记（降级即破坏）

`format` 是整个仓库里唯一一个"决定其他一切怎么读"的对象，它的两种失效都是静默
数据损坏，而不是崩溃——所以单独列一节。

| 场景 | 修复前的行为 | 现在 |
|---|---|---|
| 新版本写的仓库被旧版本打开 | `FORMAT` 解析了但**从不校验**，`OpenRepo` 返回 `nil` | `formatVersion` 上限校验，拒绝并报 `ErrFormatTooNew` |
| 未知字段经过一次读-改-写 | 白名单之外直接丢弃，`Marshal` 从结构体重建，**字段消失且不报错** | `Format.Extra` 原样保留，`Marshal` 回写 |
| 未来字段不是数字（如 `COMPRESS=zstd`） | `ParseUint` 先于 key 判断，整个标记读不了 | 先判 key 再解析，未知 key 不要求是数字 |
| `FORMAT=0` | 当作合法格式 | 拒绝（本版本从未写过 0） |

**三条回写路径都要守**，只守 `OpenRepo` 不够——`svnadmin migrate` 不经过运行中的
服务端，一样能覆盖标记：

- `UpdateFormat`（`--dir-buckets` / `--chunk-avg`）
- `switchFormat`（`migrate --segments on`）
- `createRepo`（只写新库，不读旧标记）

设计原则：**认识不了 ≠ 可以丢弃**。旧版本遇到新字段必须原样搬回去，否则"降级运行
一次"就等于把新版本的设置抹掉，而且没有任何报错。

`svnadmin info` 先打印标记再 `OpenRepo`：正因为 `OpenRepo` 会拒绝未来版本，这个
顺序才让运维在拒绝发生时仍能看到仓库里到底写了什么。保留的未知 key 会显示为
`unknown-format-keys: ... (preserved, not applied by this build)`。

## 3.4 进程级隔离（panic 与指标暴露）

前几节都是"数据被删错"，这一节是"进程/信息被拖垮"，同属爆炸半径问题。

### panic 隔离

`svngod` 一个进程服务所有仓库。任何一处未捕获的 panic 都不是"一个请求失败"，
而是**同节点全部仓库一起停服**，而且日志里只有 goroutine dump，没有仓库上下文。

两个面都必须守：

| 位置 | 不守的后果 | 现状 |
|---|---|---|
| `route`（请求入口） | 一个畸形请求打死整个进程 | `defer recover()`，写 500；已提交响应则只记录不重写 |
| 后台 goroutine | 打包清理/压缩/镜像修复 panic → 进程退出 | `goSafe(name, fn)` |
| 后台**长循环** | 循环静默退出，功能永久停摆而进程看起来健康 | `recoverLoop(name, body)`，单轮 panic 不影响下一轮 |

`recoverLoop` 比 `goSafe` 更隐蔽也更重要：循环挂掉不会有任何用户可见错误，
下次巡检才发现压缩已经几个月没跑。

判断能否写 500 靠 `statusWriter.committed()`：状态行一旦发出就不能再改，
硬写会破坏响应流。

### `/_metrics` 必须在认证之后

指标标签是 `repo="<仓库名>"`，覆盖 `svngod_repo_ready`、`repoRecovered`、
`scrubIssues` 等系列。原来它是 `route` 的**第一个分支**，在认证之前就返回，
等于任何能连端口的人都能枚举全部租户及其故障状态。

现在走 `authorizeMetrics`：Bearer token（`-metrics-token` / `SVNGOD_METRICS_TOKEN`）
优先，其次任意仓库凭证（Basic）；两者都未配置时保持开放——那种部署本来就没有
可认证的东西，强行拒绝只会打断现有单机安装。

注意**不能复用 `authenticate`**：它在无凭证时返回 `anonymous, true`（留给 authz 决定），
对指标端点等于完全不设防。必须显式要求凭证。

`MetricsToken` 已加入 `Config.Redacted()`，否则会从管理 API 的 `/config` 泄漏回去。

## 4. 校验与可观测性

`verify --all-revs` 必须保持以下覆盖，缺一项就是盲区：

| 检查项 | 实现 |
|---|---|
| segment 索引连续覆盖到 HEAD | `verifySegmentIndexes` |
| segment 对象摘要 | `fullReads` + `verifySegmentFull` |
| 每个 chunk 的 sha256 + 整体 md5 + 总长 | `verifyNode` chunked 分支 |
| 外部文本流式 md5（O(1) 内存） | `verifyNode` TextRepExternal 分支 |
| 目录对象按内容哈希 | `verifyNode` KindDir 分支 |
| WORM 哈希链 | `VerifyJournalChain` |

改动上述任一分支后，`svnadmin verify --all-revs --texts` 必须仍能对
**故意损坏的对象**报出问题。测试方式：破坏一个对象，断言 verify 报告 Issue。

## 5. 已知的合理边界（不是缺陷，不要"修"）

写下来是为了避免后人误改：

- **`segmentEntryAt` 每次复制 block/props**：看似浪费，但不复制会让 `blockCache`
  里一个小条目持有整段 0.5 MiB 的底层数组，verify 2 万修订的仓就 OOM（有过事故）。
- **`readLease` 的 `count >= 1`**：见 3.1，条件删除兜底。
- **`CommitBatch` 部分成功**：见 2.2，服务端并发合并依赖它。
- **`deletePrimaryOrAll` 只删主副本**：standby 残留无害，镜像数千次删除会打垮 standby 写预算。
- **dump 尾部比头部慢约 4 倍**：祖先节点天然分散 + 每段都要解码校验，
  不是缓存策略问题（已实测排除 5 种方案，见《性能基线与回归.md》）。

## 4.9 解析层模糊测试（2026-11 首轮结果）

输入全部来自对端：`svndiff` 解码客户端提交的 delta，`parseSkel` 解 HTTPv2 事务体
（部分路径在认证之前），`UnmarshalFormat` 读格式标记。这三个函数各写了 fuzz 目标，
**首轮就找出四个真实缺陷**——都不是理论问题，都能被单个请求触发。

| 缺陷 | 后果 | 位置 |
|---|---|---|
| `readUint` 左移无溢出检查 | varint 回绕成负值，切片下标为负 → **panic** | `svndiff.go` |
| `npos+int(length)` 溢出 | 绕过边界检查 → **panic** | `Apply`、`ApplyToSource` |
| `actionTarget` 的 `length` 无上限 | 前向自拷贝循环跑 2^60 次 → **进程挂死** | `Apply`、`ApplyToSource` |
| `SEGMENT_FROM` 单独出现 | `Marshal` 会补 `SEGMENTS=1`，改写后**存储模式变了** | `format.go` |

第四条最阴：`Unmarshal` 得到 `Segments=false`，但 `Marshal` 的条件是
`f.Segments || f.SegmentFrom != 0`，所以「读进来再写出去」等于把仓库切成段模式。
和我上一轮加的 `Format.Extra`（保留未知 key）是同一类问题——只是发生在已知字段上。
修法是读取时归一化：`SegmentFrom != 0` 就置 `Segments = true`。

另有一条 fuzz 声明的不变量是错的，保留了这条记录：我最初断言
`IsDelta` 为真则 `Version` 必须 ≥ 0，但两者的职责不同——`IsDelta` 只看 3 字节魔数，
`Version` 还要校验版本字节，所以「魔数对但版本不支持」是 `true` + `-1`，
`Apply` 随后给出明确错误。断言改成单向：`Version >= 0` 蕴含 `IsDelta`。

### 为什么两个解码器要分别 fuzz

`Apply`（内存）和 `ApplyToSource`（流式）是两份独立实现，缺陷也确实各有一份：
`maxSectionLen` 上限原本只有流式版有。只测一个等于放过另一个。

### CI 怎么跑

语料提交在 `testdata/fuzz/`，每次 `go test` 都会回放（`-run '^FuzzApply$'` 即跑种子
+ 语料）。CI 另加一段限时搜索（`FUZZTIME`，默认 20s，`0s` 只回放）。语料的价值在于
**每个文件都是一个曾经的失败**，所以回放本身就等于回归测试；限时搜索只是找新问题。

每个缺陷另外写了独立单测（`fuzz_regression_test.go`），不依赖 fuzz 复现——语料只在
有人 fuzz 那个目标时才跑，单测每次都跑。

## 4.10 连接数上限（唯一在请求之前生效的限制）

`MaxConcurrentUploads` 限的是**上传体并发**，但它在 handler 里才生效——那时 socket、
goroutine 和读缓冲都已分配。没有东西限制能开多少连接，所以对端只要开一堆 socket 不发
数据，就能耗尽 fd 让服务停止接受正常客户端。参考机软限制只有 **1024**，几百个连接
就到了，不是理论风险。

`-max-conns`（JSON `max-conns`，默认 512，0 = 不限）在 `net.Listen` 之后包一层
`connLimiter`。

### 为什么不用 `x/net/netutil.LimitListener`

它的语义是「满员时在 `Accept` 里阻塞」：连接被 accept 了但永不响应，客户端只能干等。
实测对照（同样 2 个上限、第 3 个连接）：

| 实现 | 第 3 个连接的表现 |
|---|---|
| `x/net/netutil.LimitListener` | `i/o timeout`（挂住 1.5s+） |
| `connLimiter`（本项目） | `connection reset by peer`（0.00s） |

超限就用 RST 立即拒绝，客户端马上退避；同时 `Accept` 不阻塞，优雅关闭不会被卡住。
测试断言专门区分这两者——「挂住」也算失败，否则一个更差的实现也能过。

### 两个容易写错的地方

- **槽位必须只释放一次。** `limitedConn.Close` 用 `sync.Once` 包住：重复释放会让有效
  上限悄悄变大，这种 bug 只在长时间运行后才显形。有 20 轮churn 测试守着。
- **`ListenAndServe` 换成了显式 `net.Listen` + `Serve`。** 不这样就没地方插 listener；
  换掉后必须确认优雅关闭仍然排空在途请求（`TestServeWithShutdownDrains` 覆盖）。

## 4.11 认证失败限流

失败登录原本只进审计、不减速。但一次失败并不便宜：本地密码表要跑迭代 SHA-512crypt
或 bcrypt，LDAP 后端要一次出网往返（search+bind 是两次）。几百个并发猜测就会吃掉真实
CPU 和连接槽位，而正常客户端排在后面。

两个维度同时计，因为单独任何一个都能绕过：

| 维度 | 默认预算 | 防什么 |
|---|---|---|
| 单用户名 | 10 / 窗口 | 猜某一个账号的密码（主要威胁） |
| 单来源地址 | 100 / 窗口（= 用户预算 ×10） | 一台机器狂刷**大量不同**用户名 |

**地址预算必须比用户预算宽得多。** 地址是共享的：办公室 NAT、CI runner 池、反向代理
都表现为一个地址。地址阈值设得紧，一个人打错几次密码就会锁掉同一出口后面的所有人——
防御变成拒绝服务。这个 10 倍差距是实测出来的：第一版两个维度同阈值，
`TestLimitIsPerSourceAddress` 立刻失败。

只计失败，成功永不限流。成功**只清自己身份的计数**，不清别人的。

语义上 `0` 是「未设置→用默认」，`-1` 才是禁用。JSON 里省略字段会解析成 0，
把 0 当禁用会让「其它都配得很仔细」的部署静默丢掉限流。

### 不信任 X-Forwarded-For

按 `RemoteAddr` 计数，不看 `X-Forwarded-For`：后者除非代理强制覆写，否则由客户端控制，
信任它等于让攻击者每次换一个身份，限流完全失效。需要按真实客户端限流的部署应在代理层做。

### 内存有上限

地址轮换攻击不能把表撑爆——否则把 CPU 问题换成内存问题。`maxThrottleEntries` 到顶后
先清过期条目，仍然满就整体重置（代价是洪水期间大家预算短暂归零，但内存有界）。

## 4.12 请求体总大小上限

各 handler 本来有各自的限额（skel 体 1 MiB、PROPFIND 8 MiB、PUT 64 GiB、bundle 1 TiB），
但**没有一个覆盖整个请求的兜底**。两个缺口：

- 以后新增的 handler 若忘了设限，没有任何保护；
- `Content-Length` 说谎（chunked，或头部远小于实际）的请求从不与任何上限比较。

上限放在 `countingReadCloser` 里——这是**每个请求体都必经的唯一位置**，它本来就在统计
字节数（指标用）。在那里限流意味着所有路径自动继承，而不是靠每个 handler 记得。

### 一个必须处理的细节：413 会被 handler 抢先写掉

handler 读到 `http.MaxBytesError` 后行为不一致：有的映射成 400，有的直接吞掉当成功
（实测回 **200**）。而 HTTP 状态行一旦写出就改不了。

所以包装器超限时通过 `onOver` 回调把 `statusWriter.suppressed` 置真：handler 之后写的
一切被丢弃，`route` 的 defer 再解开抑制、写 413。反向验证时这两个机制各自被证明必要：

| 移除 | 实际返回 |
|---|---|
| `route` 的 413 映射 | **200**（handler 把超限当成功） |
| `onOver` 抑制 | **400**（handler 的猜测覆盖了真实原因） |

### 默认值

`1 TiB`（`-max-body-bytes`，0 = 默认，-1 = 不限）。必须高于所有分 endpoint 限额，
否则正常请求会被拦：PUT 允许 64 GiB。实测 5 MB 文件经真实 `svn` 客户端提交/检出后
sha256 一致，确认未被误伤。

## 4.13 S3 读挂死（调用方 ctx 无 deadline 时的兜底）

`internal/fs` 大量用 `context.Background()` 调存储层。S3 适配器直接把这个 ctx 传给
minio，于是**没有任何 deadline**。三种既有保护都盖不住「网关发完 header 就卡住 body」：

| 保护 | 为什么不管用 |
|---|---|
| `ResponseHeaderTimeout=30s` | header 到达时计时器就停了 |
| minio `MaxRetries=2` | 只重试传输错误，不管「读了永远不返回」 |
| 调用方 ctx | 传的是 `Background()`，无 deadline |

后果是**永久挂死**：占住一个 goroutine；在提交路径上还占着 commit lease，整个仓库写不进去。

修法是在读空闲上设上限（`readIdleTimeout=30s`），不是整体时限——512 MiB 对象合法地要读
几分钟，整体 deadline 要么没用要么误伤大对象。每次成功读取重置计时器。

覆盖三条路径：`Get`（`io.ReadAll`）、`GetTo`（`io.Copy`）、`Head`（`StatObject` 读空 body）。

### 一个被连带的放大问题

`retry` 看到 `context.Canceled` 时原本会继续重试。idle timer 取消的是内部 ctx，外层
ctx 未取消，于是**一次 30s 卡顿被放大成 4×30s**。现在 stall 返回 `noRetryError`，
且 `retry` 在 `ctx.Err() != nil` 时立即停止——这两处都是必要的。

### 验证

- stub 网关（发 header 后停写）：Get/Head 在 33s 内返回，不再无限挂死；调用方传 300ms
  deadline 时 3.3s 内返回（尊重更紧的调用方约束）
- 真实 S3（192.168.23.228）：Put/Get/Head/GetTo 全部正常，24 字节往返一致

### 顺带修掉一个从未跑过的断言

`s3store_integration_test.go` 里 `st.Get(...) != ErrNotFound` 用的是**精确比较**，
而 `Get` 一直返回 `fmt.Errorf("%w: %s", ErrNotFound, key)`（带 key 便于排障）。
这个测试只在设了 `S3_ENDPOINT` 时才跑，CI 从来没有该变量，所以断言一直是错的却没暴露。
改为 `errors.Is`。

## 4.14 quorum 写的聚合等待（副本不响应取消时）

`quorumMirror` 给每个 standby 副本一个 `quorumWriteTimeout`(15s) 的 context，然后
`wg.Wait()`。**超时只有在 `fn` 真的响应取消时才有用。**

如果后端忽略 ctx（SDK 内部阻塞在 syscall、客户端库不轮询 ctx、某个库的 bug），
`WithTimeout` 就是空操作，`wg.Wait()` 随之**永久等待**。提交路径上这意味着调用方
永远拿不到响应、commit lease 永不释放——后续所有提交排在这一笔后面。

| 层 | 兜底 | 对「忽略取消」是否有效 |
|---|---|---|
| 单副本 ctx 超时 | 15s | **无效**（前提是 fn 遵守取消） |
| `wg.Wait()` | 无 | 无上限 |

修法：把聚合等待换成 `select` + `quorumWriteTimeout + grace(3s)`。超时后：

- 未 ack 的副本按 `markDownHung` 处理——不只是标记不可用，还强制下次 repair
  **枚举对象**而非信任 pending delta（写进 socket 缓冲但未处理的数据不能算已写）
- 返回值仍是 `ErrQuorumUnmet`：没 ack 的副本不是已 ack 的副本，不能谎报成功

**一处必须注意的并发**：超时分支返回后 goroutine 仍在跑，会继续改 `ok`。所以读取
ack 计数必须持锁快照，否则既是数据竞争，也可能报出一个从未同时成立的数字。

### 验证

用「完全忽略 ctx」的 store（最坏情况）驱动：

- 原代码：`Put` 永不返回（35s 后测试放弃）
- 修复后：18s 内返回并报 `ErrQuorumUnmet`
- 健康两副本：正常成功（不误伤）
- 回退聚合超时 → 测试重新挂死；回退错误返回 → 测试抓到「谎报成功」
- `-race` 全绿（含既有 `TestMirror*` 全系列）

## 4.15 请求路径上的并发批次也没有聚合上限

和 4.14 同一类问题，但在请求路径上：`loadChangeFragments` 并行读事务的变更片段
（`fragmentParallelism=32`），然后 `wg.Wait()`；调用方是 `loadTxnChanges`，传的是
`context.Background()`。`http.Server` 只设了 `ReadHeaderTimeout`/`IdleTimeout`，
**故意没有 `ReadTimeout`/`WriteTimeout`**（多 GB 上传是预期场景），所以请求 ctx 也没有
deadline。存储卡住时这个函数永不返回，提交请求一起挂住、它派生的 goroutine 全部滞留。

### 两段都要有界，而且共享一个预算

只给 `wg.Wait()` 加超时不够。**信号量的获取在派发循环里**：32 个 worker 全卡住后，
第 33 次 `sem <- struct{}{}` 会永久阻塞，派发循环根本走不到后面的等待——超时是死代码。
所以派发和等待都要能被同一个 deadline 打断。

而两段各用一次 `time.After(fragmentReadTimeout)` 会让最坏情况变成 2×30s 串联。正确做法
是用 `context.WithTimeout` 派生一个 ctx，两处都 select `Done()`——`time.After` 的 channel
只有一个值，会被先到的 select 取走，另一处永远等不到。

### 并发细节

超时分支返回后 worker 仍在跑、继续写 `out[i]`/`ok[i]`。所以合并结果必须持锁——否则既是
数据竞争，也可能把一个正在写的片段当成已完成。

### 验证

用忽略 ctx 的 store 驱动：

| 场景 | 结果 |
|---|---|
| 修复前 | 永不返回（5s 断言放弃） |
| 修复后 | 30s 内返回 |
| 32+ 片段（全部槽位占满） | 30s 内返回（派发也被打断） |
| 健康路径 | 正常（0.00s） |
| 禁用 deadline | 测试重新挂死（40s 超时） |
| `-race` | 全绿（含 `TestBundle*`/`TestTxn*`） |

## 4.16 Bundle 分块路径的两处无界等待

4.15 修的是事务变更片段；bundle 上传的分块路径有四点和它不一样，所以单独一节。

### 两条路径，都是 16/8 个 worker + 有界 channel

`handleBundleChunks`（存在性查询，16 worker）和 `storeChunksParallel`（分块写入，
8 worker）都把活投给 worker。**投递本身会阻塞**：worker 全卡在存储里，channel 缓冲
填满，生产循环停在发送上，永远走不到 `wg.Wait()`。和 4.15 的信号量是同一个陷阱——
只给等待加超时会是死代码。所以投递也进了 `select`。

### `storeChunksParallel` 有 6 处 `wg.Wait()`，其中 5 处是错误清理

`close(jobs)` 后等 worker 排空。校验和不匹配是在 worker 还在 `Put` 的时候发现的，
所以**连提前返回的错误路径也会挂住**。6 处全部改走 `waitBounded`。

### 超时不能报成功——这是本轮最危险的一点

`storeChunksParallel` 原来返回 `firstErr`。超时时 `firstErr` 很可能是 nil（worker 只是
卡着，没报错），直接返回就等于**告诉客户端上传成功，而分块可能没落盘**。现在超时且
`firstErr == nil` 时返回 `errBundleChunkStore`。

`handleBundleChunks` 同理但更隐蔽：它返回 `missing` 列表。超时后未查询的 hash 不在列表
里，客户端会理解为「这些分块已存在」，于是跳过上传——**数据静默丢失**。现在超时返回
503 而不是部分列表。

### 验证

用布防式 stall store（`CreateRepo` 要写配置，所以必须建完仓库再布防）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 40 分块，Put 全卡（缓冲满） | 挂死（producer blocked on full channel） | 30s 返回 |
| 校验和失败（错误清理路径） | 挂死（cleanup wait blocked） | 30s 返回 |
| 40 hash 查询，Exists 全卡 | 挂死（请求不返回） | 30s 返回 503 |
| 健康写入 12 分块 | 通过 | 通过 |
| 健康查询 40 hash | 通过 | 通过 |
| `-race` | — | 全绿（含 `TestBundle*`） |

⚠️ 第一版测试是无效证据：stall store 从构造起就阻塞，`fs.CreateRepo` 在建仓库时
写配置即死锁，测试根本没跑到被测代码。加了 `armed` 开关后才测到真东西。

## 4.17 三条"看起来部署好了、其实不能用"的缺陷

前四轮修的是请求路径挂死。这一轮是发布前的可运维性审查，找到的三条都属于**静默失效**：
进程活着、日志干净、探针 200，但功能已经不对了。

### 4.17.1 健康检查返回常量

`internal/admin/admin.go` 的 `/_api/v1/health` 原来直接写：

```go
writeJSON(w, http.StatusOK, map[string]any{"status": "ok", ...})
```

它从不参考仓库就绪状态。存储全挂、所有 self-check 失败，它依然 200 `ok`。放在 LB 或
Kubernetes readiness 后面，流量会持续打到服务不了的实例上——**这正是"部署看起来成功"的
典型故障**。

而 `Server.RepoReadySnapshot()` 早就有完整的就绪数据（启动 self-check 与热恢复都在写它），
只是 health 没用。

改法：任一仓库未就绪即返回 503 `not_ready`，并列出仓库名与原因。**没有就绪记录的仓库按
未就绪处理**——探针不能基于"没检查过"而通过。零仓库配置仍返回 ok，否则全新安装永远无法
就绪。部分失败也算失败：让部分租户报错、编排器却认为健康，是更糟的状态。

### 4.17.2 镜像临时文件落在 /tmp，且清理正则漏了前缀

镜像写要把整个对象缓冲一份（standby 需要第二次读同样的字节），走
`os.CreateTemp("", ...)`，也就是 `os.TempDir()`。对象上限 64 GiB，所以临时文件同量级：

- 容器里 `/tmp` 常是 tmpfs → 一次大提交**吃掉内存**
- 或者是个小分区 → **ENOSPC**
- 两条都要等到有人提交大文件才暴露

而且全仓 7 处 `CreateTemp("", ...)` 分散在 4 个包，没有统一入口。

处理：
1. `-temp-dir` flag，启动时 `os.Setenv("TMPDIR", dir)`。`os.TempDir()` 读 TMPDIR，所以
   一处设置覆盖全部 7 个调用点，不必改 7 处代码。目录不存在就建，并**真实写一个探针文件**
   验证可写——坏路径在启动时报错，而不是在第一次大提交时。
2. 补全清理正则。原正则 `svngod-(?:body|delta|text|txn|put|mirror)-(\d+)-` 漏了 4 类，
   实测确认：

| 前缀 | 原正则 | 后果 |
|---|---|---|
| `svngod-mirror-fast-<pid>-` | ❌ | 大对象流式镜像留下半写文件 |
| `svngod-stream-<pid>-` | ❌ | 大文本外发留下整份副本 |
| `svngod-repair-<pid>` | ❌ | 修复中断的文件永不回收 |
| `svngod-recover-<pid>` | ❌ | 同上 |

注意 `repair`/`recover` 的 pid 在**最后**（`CreateTemp` 直接把随机后缀接在 pattern 后），
和其余几种的 `<pid>-` 形态不同，所以正则分成两个分支。

**这类漏项没有报错、没有日志，只是磁盘慢慢满**——所以测试直接以"每一种真实 CreateTemp
前缀"为表，漏一个就红。

### 4.17.3 修复循环的两个 join 没有上限

`repairInternal` 给每个 mirror 的 listing 和每个复制 worker 都设了超时，但两个聚合等待
（列表后的 `wg.Wait()`、复制后的 `cw.Wait()`）没有上限。忽略取消的存储会把 goroutine
永久挂住，于是整轮修复永久挂住——**而修复是备机恢复的唯一机制**。

和前几轮同源。但这次多了一步，也是最关键的一步：

### 超时后不能继续读 worker 的共享状态

第一版修复只是把 `wg.Wait()` 换成有界 join，然后**照常继续往后读** `sets[i]`、
`reachable[i]`、`missing[]`、`failed[]`。这些正是 worker 正在写的字段。`-race` 直接
报了 6 条数据竞争，而且逻辑上更糟：可能读到"某镜像不含任何对象"就把它标成健康。

正确做法是**超时即放弃本轮**，返回，什么都不读。下一轮从头重列，不丢任何东西。

这个决策本身也做了反向验证：把 `return` 去掉、恢复成"继续读"，`-race` 立刻复现 6 处竞争。

### 测试基础设施的一个坑

第一版测试把修复超时改成**包级 var** 让测试缩短它，跑单测全绿，全量 `-race` 却红了：
另一个测试的后台 `recoveryLoop` 正在读那个 var。

改成 `MirrorStore` 的实例字段 + 访问器方法。测试改自己的实例，互不干扰。

### 验证

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 全部仓库 not ready，查 health | 200 `ok` | 503 `not_ready` + 仓库名与原因 |
| 部分仓库 not ready | 200 `ok` | 503 |
| 零仓库配置 | 200 `ok` | 200 `ok`（保持不变） |
| 陈旧 `mirror-fast`/`stream`/`repair`/`recover` 文件 | 不回收 | 回收 |
| 清理时保留活进程/自身/无关文件 | — | 通过 |
| 复制阶段存储不回 ctx | 永久挂死 | 放弃本轮并返回 |
| 列表阶段存储不回 ctx | 永久挂死 | 放弃本轮并返回 |
| 超时后继续读 worker 状态 | — | `-race` 报 6 处竞争 |
| 健康镜像仍需完整复制 | 通过 | 通过（无误报） |
| 全量 CI | — | OK，14 包 `-race` 干净 |

## 4.18 请求体的时间维度：三个互不重叠的界限

`4.x` 前几节处理的是"等待没有上限"，这一节是同一类问题在**请求体**上的另一面。

请求体此前只有大小上限（`4.4` 相关的 `max-body-bytes`）。大小上限管的是**多少**，
管不了**多久**：一个每秒发 1 字节的客户端永远在限额内，却可以无限期占着连接、
goroutine、上传槽位。`ReadHeaderTimeout` 帮不上忙——它在 body 之前就结束了。

### 两种失败形态，需要两种手段

| 形态 | 客户端行为 | 为什么单一手段无效 |
|---|---|---|
| 拖沓 | 持续但极慢地发数据 | 每次 `Read` 都正常返回，读 deadline 永远不会触发；只有**平均速率**能发现 |
| 静默 | 完全不再发数据 | 字节计数停止增长，任何基于计数的判断都看不到它；只有**读 deadline** 能打断内核里的阻塞 |

所以两个都要有，且必须分开配置。

### 实现位置：复用已有的字节计数器

`countingReadCloser`（`internal/server/metrics.go`）本来就是所有请求体的唯一通道，
大小上限就放在那里。速率判定接在同一个地方，新端点自动继承，不需要每个 handler 记得。

判定用「累计字节 / 从首次读起的耗时」，宽限期（默认 30s）内不判定——建连、
TLS 握手、客户端首次读盘的停顿都发生在这个窗口，用它们算平均会误伤正常客户端。

### 一个只有真实连接才能发现的缺陷

第一版把读 deadline 交给 `http.NewResponseController(w).SetReadDeadline`。
测试用 `httptest.NewRecorder()`，它没有底层连接，注入一个假的 setter 就能验证
"deadline 被设置了"。**这个测试通过了，而修复完全没生效。**

原因：`route` 把 `w` 换成了 `statusWriter` 包装。`http.ResponseController` 靠
`Unwrap() http.ResponseWriter` 向下穿透，而 `statusWriter` 没有这个方法，于是
`SetReadDeadline` 返回 `ErrNotSupported`，被 `armStall` 里的 `_ =` 吞掉。
表现是：静默客户端一直挂着，和没修一模一样。

补上 `Unwrap()` 后，用一个真实 TCP 连接、声明 `Content-Length` 只发一半再静默的测试
才把它测出来——并且断言的是**读返回的错误类型**（`EOF` 而非超时），
因为"客户端自己的 deadline 到了"也会让 `ReadAll` 返回，那样的测试什么也证明不了。

### 验证

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 拖沓 body（1 KiB/s，下限 1 MiB/s） | 一直读下去 | 宽限期后 `408` |
| 突发但平均达标 | — | 通过（无误报） |
| 静默连接（真实 TCP，只发一半） | 挂到客户端放弃 | 恰好 2m0s 切断，`408` |
| 无 body 的 PROPFIND | 207 | 207，5ms |
| 真实 `svn` 客户端 checkout/commit/copy/delete | — | 全部通过（无误报） |
| `statusWriter` 缺 `Unwrap()` | deadline 静默失效 | 测试失败并指出原因 |
| 速率超限的响应码 | — | `408` 而非 `413`（排除误导向大小上限） |

### 测试基础设施的一个坑（同 `4.17`）

`TestKeepAliveRequestStillWorksAfterAStalledPeer` 验证"关闭后连接可复用"，
它在**去掉 `Close` 里的 deadline 清理后依然通过**——因为 `net/http` 在开始读下一个
请求时会自己重置 deadline。一个不会失败的测试等于没有测试，所以删掉了它，
并把 `Close` 的注释改成如实描述（它不为 keep-alive 正确性负责，
只是不让包装器留下依赖他人清理的状态）。

## 4.19 鉴权路径与解析路径必须是同一个字符串

这一节是本批次最严重的发现：**授权检查的路径和处理器实际读取的路径不一致**，
两者只要不一致，authz 再严也等于没配。

### 三层各写一套 `..` 语义

| 层 | 位置 | 对 `..` 的处理 |
|---|---|---|
| URL 解析 | `parseResource` → `splitPath` | 保留 |
| 授权 | `authz.normalizePath` | 只丢 `""` 和 `"."`，**保留** `..` |
| 文件系统 | `fs.segments` | **丢弃**（从不向上走） |

于是 `/svn/demo/../private/secret.txt`：
- authz 拿 `/../private/secret.txt` 匹配，**匹配不到** `[demo:/private]` 的拒绝规则，回落到 `[demo:/]` 的 `* = r` 放行；
- fs 把同一路径解析成 `/private/secret.txt`，读出内容。

实测：直接路径 403，加 `..` 后 200 + 密文。

### 写入形态同样成立

真实 DAV 流程（MKACTIVITY → CHECKOUT → PUT）：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `PUT .../txn-a-1/private/keep.txt` | 403 | 403 |
| `PUT .../txn-a-1/../private/keep.txt` | **201** | 409 |
| `PUT .../txn-a-1/./private/keep.txt` | — | 403 |
| `PUT .../txn-a-1//private/keep.txt` | — | 403 |

提交时的逐路径复核（`commit.go` 的 `az.Authorize(user, repo, ch.Path, true)`）也拦不住，
因为它同样拿字面 `..` 路径去问 authz。

### 修复：入口归一化 + 授权层兜底

两处都改成 `path.Clean`，**不是**只为兼容，而是让"授权看到的路径"与"处理器使用的路径"
由构造决定相同，而不是靠三份实现碰巧一致：

- `splitPath`（url.go）先 `path.Clean`，7 处 `path:` 构造全部受益；
- `authz.normalizePath` 也 `path.Clean`，规则解析与请求匹配用同一语义。

两层各自独立有效——单独回退任一层，对应测试都会失败：

| 回退 | 失败测试 |
|---|---|
| `splitPath` 不 Clean（authz 仍 Clean） | `TestAuthzDotDotCannotReadDeniedPath`（200 + 密文） |
| `authz.normalizePath` 不 Clean（url 仍 Clean） | `TestAuthorizeResolvesDotDot` |
| 两层都不 Clean | 两者都失败 |

只回退一层时集成测试仍通过，因为另一层在兜底——这正说明纵深有效，
但也说明**必须为每层写单层测试**，否则"集成测试绿了"会掩盖某一层已经失效。

## 4.20 管理接口凭据泄露（两处）

`Redacted()` 是管理 API 与存储凭据之间的唯一屏障，但有两个漏洞。

### 4.20.1 单仓库 GET 绕过了 Redacted()

`GET /_api/v1/repos/<name>` 直接返回活的 `*config.Repo`，而 `config.Repo` 会原样序列化
`storage.access-key`、`storage.secret-key`、`auth[].bind-password`。

同服务的 `GET /_api/v1/config` 走的是 `Redacted()`——同一个进程里两种行为，
说明这不是设计取舍，是漏了。持有一个"管理仓库"用途的 token 就能读到 S3 密钥和
LDAP 服务账号密码，而这类凭据通常跨系统复用。

修复：返回 `Redacted()` 的副本。测试 `TestRepoByNameDoesNotDiscloseStoredSecrets`
同时检查两个端点，并要求 `TestRepoByNameStillReturnsTheRepo` 保证没有"修成返回空"。

### 4.20.2 redactStore 只递归 Mirrors

geo 与 sharded 形态的密钥藏在 `Local` / `Remote` / `ShardMeta` / `ShardRanges[].Store`
里，`redactStore` 只递归了 `Mirrors`，这些全部明文。

可达性说明（不要夸大）：`Validate()` 只接受 `file|s3|mirror`，所以 geo/sharded 仓库正常
建不起来。但配置加载失败时，`runMultiRepo` 仍把**未经删改的整个 cfg**（含那个失败仓库）
交给 `startAdmin`，于是 `/_api/v1/config` 照样能读到它们的嵌套密钥。

同时补上 `SecretKeyFile`：指向密钥文件的路径和密钥本身一样敏感。

## 4.21 发布之后的失败，不能报成提交失败

两条缺陷同一类：**修订已经可见，却告诉客户端失败**。客户端于是重试一个已应用的提交，
得到 out-of-date，或产生重复后继。

### 4.21.1 打包失败把成功提交变成失败

`commitTxn` 在 HEAD CAS 之后还执行 shard 自动打包，失败时 `return N, err`。

复现（`packFailStore` 注入：HEAD CAS 之后的打包写失败）：

```
commit reported error ... but published revision 2 (head=2)
```

**判定：打包失败应记日志并报成功**，理由是可以逐条核实的：

- 此刻修订已持久、HEAD 已推进，提交**确实发生了**；
- 打包是纯合并步骤：只把 loose 对象改写成 packed 形式，`isPacked` 短路保证幂等；
- 数据不以 packed 形式存在也完全可读（`TestAbandonedPackLeavesRepositoryReadable` 断言两版内容都能读回）。

batch 路径原本就是这么处理的（只 `log.Printf`），v1 路径是唯一的例外。

### 4.21.2 放弃之后必须有重试，否则省对象的目的落空

只改成"报成功"会留下一个坑：打包**只在关闭 shard 的那次提交时触发**，
而 GC（`CollectLooseProgress`）只删除**已打包** shard 的 loose 副本，不会主动打包。
也就是说打包失败后没有任何机制再补 —— 该 shard 的 loose 对象永久留下，
O(shards) 的对象预算被破坏，而这正是打包存在的理由。

实测确认：`PackShard` 无任何调用方，也没有 `svnadmin pack`；唯一触发点是提交路径。

所以补了一个后台重试队列（`enqueuePack` / `packLoop`），与段库的 `compactQ` 同一模式，
并且**有界**：5 次尝试、指数退避（1s→2s→4s→8s）。无界重试会在另一个写者持续持有提交租约时
永久自旋（提交刚结束时租约正被占用，这是最常见的情况），并让 goroutine 和队列活到进程结束。

失败时先入队再清 `revs` 的那个测试，回退掉入队调用会失败：

```
shard 1 was never packed after the retry (packed=false err=<nil>)
```

### 4.21.3 v1 CommitBatch 的 CAS 竞争报出未发布的修订号

CAS 输给对端 WAL 回放时，`batch.go` 只给非自己拥有的 plan 设 `errs`，
**没有清零 `revs`**；`segment_commit.go` 对应位置是清零的。

复现（`racStore` 在对端发布 revision 2 后让本次 CAS 冲突）：

```
request 1 reported revision 3 but head is 2: that revision was never published
```

危害在 `svnadmin load`：它只检查 `err` 与 `rv == 0`，非零就 `lastRev = rv`，
于是把从未写入的修订当成成功，后续修订叠在错误的基线上，恢复时静默丢历史。

修复对齐段库：非拥有即 `errs[p.idx] = store.ErrQuorumUnmet; revs[p.idx] = 0`。

### 验证

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 打包失败 | 返回 error，但 head 已推进 | 记日志 + 入队重试，提交报成功 |
| 打包失败后重试 | 无任何重试路径 | 后台补打包，`isPacked` 为真 |
| 重试持续失败 | — | 5 次后放弃并记日志，数据仍可读 |
| v1 CAS 竞争 | 报出未发布的 revision 3 | 非拥有即清零，与段库一致 |
| 段库 CAS 竞争 | 已正确 | 不变（回归测试通过） |

## 5.0 版本可追溯（排障第一问）

线上出问题时第一个问题是"跑的是哪个构建"。回答不了，后面的分析都是在猜。

`internal/version` 提供 `Version`/`Commit`/`BuildDate`，由 `scripts/build.sh` 用
`-ldflags -X` 注入；三个二进制的 `--version` 都先于任何参数校验处理（`svngod` 不需要
`--repo-root`，`svnadmin` 不需要子命令）。

回退顺序，每一层都有明确语义：

| 情况 | 输出 | Unreleased |
|---|---|---|
| 注入 `1.2.3` | `1.2.3 (commit abc123, built ...)` | false |
| `go build` 在 checkout 里 | pseudo-version + `+dirty` 若有改动 | true |
| `go install` 打了 tag 的模块 | `v0.9.1 (commit ...)` | false |
| 无 build info | `dev` | true |

两条容易写错的规则：

- **未注入时不能编一个版本号。** 声称 `1.0.0` 会让本地构建与正式发布无法区分，
  所以回退到 `dev` 并置 `Unreleased`。
- **显式注入的版本不带 `-dirty`。** 发布构建经常在未提交的树上切，但产物就是那个
  版本；加 `-dirty` 会让刻意的发布看起来像本地实验。只有工具链推导的版本才标 dirty。
- `+dirty-dirty` 这个 bug 真实出现过（工具链已加 `+dirty`，代码又加一次），
  已有测试锁住。

**仓库不再提交二进制产物。** 曾有一个 14 MB 的 macOS arm64 `svnadmin` 被误提交
（`27db5f2`），`.gitignore` 也已补上 `bin/` 与三个二进制名。发布产物走
`scripts/build.sh` 输出到 `bin/`，不进版本库。

## 5.1 CI 门槛（改数据路径后必须全绿）

`scripts/ci.sh` 是唯一权威门槛，本地和 CI 跑同一份：

| 步骤 | 作用 | 跳过开关 |
|---|---|---|
| gofmt / vet（linux+darwin） | 格式与静态检查 | — |
| build（linux+darwin, CGO_ENABLED=0） | 发布形态可构建 | — |
| `go test`（CGO_ENABLED=0） | 主测试套件 | — |
| **`go test -race`（CGO_ENABLED=1）** | 并发正确性 | `CI_SKIP_RACE=1` |
| restore drill | 备份恢复链路 + 拒绝损坏备份 | `CI_SKIP_DRILL=1` |
| svn client | 真实 svn 客户端端到端 | `CI_SKIP_SVN_CLIENT=1` |

**govulncheck 为什么只对可达漏洞失败**：govulncheck 分三层——符号可达、
包已导入、模块在依赖图中。三层都判失败会让门槛永久红灯：目前 `x/crypto` 被标记
（其 openpgp 包"不再维护、设计上不安全"），但 svngod 根本不导入 openpgp（它经由
go-ldap 间接引入，用于 NTLM），唯一"修复"是伪版本。门槛一旦无法变绿就会被无视，
所以模块级只打印不阻塞，包级打印警告，符号级才失败。

连带的一次真实清零：升级 `golang.org/x/net` 0.57→0.62、`x/crypto` 0.54→0.58、
`x/text` 0.40→0.43、`x/sys` 0.47→0.49、`klauspost/compress` 1.17→1.20 后，
可达 0、包级 0。其中 `compress/s2` 的越界读（GO-2026-5841）原本就挂在我们导入的
store 包链上，属于压缩/解压路径，值得优先处理。

脚本自身踩过的坑：`printf '%s\n' "$OUT"` 里 `$OUT` 是临时文件**路径**不是内容，
拿它去 grep 会让每一次"扫描失败"都被报成"发现漏洞"——排障方向直接被带偏。现在
区分三种非零：有 `Vulnerability #` 行才算漏洞，否则报"扫描未完成，既不清白也不是发现"。

**`-race` 为什么单独一遍**：发布构建是纯 Go 静态（`CGO_ENABLED=0`），而 race 检测器
依赖 cgo，两者不可能在同一遍里完成。`fs`/`server` 有真实并发（组提交、镜像修复、
事务清理），那里的竞争不是"答案算错"而是"数据写坏"，所以这一遍不能省。全量约 19 秒。

校验它**真的会报警**（不是跑了个寂寞）：在 `CommitTxn` 入口加一句无锁自增，
`TestConcurrentSamePathCommit` 立刻报 `WARNING: DATA RACE`。改并发代码时值得重做这个探针。

### 一个会静默吞掉失败的 shell 陷阱

```bash
set -euo pipefail
out=$(some_command); rc=$?     # 错：rc 那行永远执行不到
out=$(some_command) || rc=$?   # 对
```

`set -e` 下赋值语句取命令替换的退出码，非零就地退出——**后面的失败分支永远不跑，
CI 静默死掉且不打印任何原因**。这比没有检查更糟：看起来"CI 失败了"，但没人知道为什么。
`ci.sh` 里 race 和 svn client 两段都踩过，都已改成 `|| rc=$?`。

同理，`printf | grep | head -60` 会让 `grep` 收到 SIGPIPE，CI 报 141 而不是真实错误；
要截断就先捕获再 `sed -n '1,60p'`。

## 6. 新增代码的自查清单

提交涉及数据安全的改动前，逐条确认：

- [ ] 任何 `continue` / 静默 `return nil` 都在"读失败但可以安全忽略"的位置，且注释说明了为什么安全
- [ ] 删除操作前，引用集/白名单的建立过程有任何读取失败都会中止整轮
- [ ] 白名单自校验了覆盖范围（不只是"存在的都收进来"）
- [ ] 新增的 `QuorumGet` 调用检查了 `count`
- [ ] 破坏一个对象的测试能证明对应的 verify 分支有效
- [ ] 如果改了 `commitTxn` / `CommitBatch`，`-race` 与混沌矩阵都跑过
- [ ] 新增的批量导入/回放调用方用的是 `AllOrNothing()`，而不是自己检查 `revs` 里的 0
- [ ] 新增代码没有依赖 `CommitBatch` 的默认部分成功语义，除非它确实需要 disjoint 合并
- [ ] 改了 `Format` 结构或 `Marshal`/`UnmarshalFormat`，确认未知字段仍被保留，且 `formatVersion` 上限仍拦得住
- [ ] 新增任何"读-改-写整个控制对象"的路径，都调用了 `checkFormatVersion`
- [ ] 新增后台 goroutine 用 `goSafe`；新增长循环用 `recoverLoop`（前者保进程，后者保功能）
- [ ] 新增需要认证的端点没有放在 `route` 认证之前，且没有复用 `authenticate` 的匿名成功语义
- [ ] 新增的机密字段加进了 `Config.Redacted()`
- [ ] 改了并发路径（组提交/镜像/事务清理），本地跑过 `CGO_ENABLED=1 go test -race ./...`
- [ ] 在 `ci.sh` 里新加的外部命令用 `cmd || rc=$?` 取退出码，否则失败分支永远不会执行
- [ ] 新增解析入口（协议/skel/格式/编解码）配了 fuzz 目标，且失败语料提交进 testdata/fuzz/
- [ ] 从输入解码出的长度在校验前先判上限，且比较用 uint64 而不是 int（溢出会绕过 int 检查）
- [ ] 新的限流/上限放在「请求之前」还是「handler 内」想清楚了：handler 内的限制挡不住连接耗尽
- [ ] 新增的限制若在 handler 内生效，确认 handler 不会把超限错误吞成 2xx（状态行写出后无法改）
- [ ] 对存储/网络的阻塞调用，若调用方可能传 `context.Background()`，该层自己要有超时兜底（别假设上层会传 deadline）
- [ ] 用 context 超时兜底并发等待时，确认被等的函数真的响应取消；`wg.Wait()` 本身没有上限
- [ ] 并发批次的上限要覆盖**派发**（信号量获取会阻塞主线程），不只是等待；两段共享一个 deadline 而非各自计时
- [ ] 等待超时后**核对返回值**：超时的批次若返回「成功」或「部分结果」，等于把未决状态谎报为已完成（bundle 分块会静默丢数据）
- [ ] 错误清理路径的等待也是等待：`close(ch)` 后等 worker 排空同样会挂在卡死的存储上
- [ ] 探针必须反映真实服务能力：返回常量 `ok` 的 health 端点会把流量导向坏实例，比没有探针更糟
- [ ] 「没检查过」不等于健康：缺就绪记录的实例按未就绪处理
- [ ] 迁移类/镜像类临时文件不要落在 `/tmp`：容器里常是 tmpfs（吃内存）或小分区（ENOSPC），且要等到大文件才暴露
- [ ] 新增 `os.CreateTemp` 的 pattern 必须同步进清理正则，否则崩溃残留永不回收（无报错、无日志，只是磁盘变满）
- [ ] 有界 join 超时后**不要继续读 worker 写的字段**：既可能触发数据竞争，也可能把半观测状态当成完整状态；直接放弃本轮
- [ ] 测试不要改包级可变配置来缩短超时：其他测试的后台 goroutine 可能正在读它，全量 `-race` 才暴露
- [ ] 大小上限之外想清楚**时间**上限：只限大小的话，每秒 1 字节的客户端永久合法规
- [ ] 用 `http.ResponseController` 前确认中间层 `ResponseWriter` 实现了 `Unwrap()`：否则 `SetReadDeadline` 静默返回 `ErrNotSupported`，而 `_ =` 会把它吞掉
- [ ] 涉及连接行为的修复必须用**真实 socket** 验证：`httptest.NewRecorder()` 没有连接，只能证明"代码被调用了"
- [ ] 断言要能区分"我成功了"和"对端超时了"：例如读返回 `EOF` 与 `Timeout` 是两种不同的结果，只看"函数返回了"等于没测
- [ ] **授权检查用的路径必须就是处理器解析用的路径**：两处对 `..`/`//`/`./` 的处理若有差异，authz 的拒绝规则会被绕过；归一化只写一处，或各自 `path.Clean` 后再比
- [ ] 新增任何返回配置的接口，确认它走的是脱敏副本而不是活对象（`config.Repo` 会原样序列化密钥）
- [ ] 给 `Redacted()` 加字段时，确认新字段里的密钥也被覆盖：递归要跟到 `Local`/`Remote`/`ShardMeta`/`ShardRanges` 这些嵌套 store
- [ ] 单层测试与集成测试都要有：多层防御下，只回退一层时集成测试仍会通过，绿色会掩盖某一层已失效
- [ ] 状态推进（HEAD/CAS）**之后**的步骤失败，一律不能改判定为失败：客户端会重试一个已应用的提交
- [ ] 把某个步骤降级为"失败只记日志"时，确认它确实有别的补偿路径；否则该步骤从此永不执行（打包曾因此永久停摆）
- [ ] 后台重试必须有界并退避：无界 requeue 在资源被他人长期持有时会永久自旋，且 goroutine 活到进程结束
- [ ] 批量接口返回的修订号，必须只在**确实可见**时非零；调用方通常只查 `err` 和 `rv == 0`
- [ ] 注入式测试的故障要"持续到显式解除"，一次性计数会在实现内部的下一次写入就漏过，导致测试假绿
