# 数据安全与原子性审计清单

本文件是**可复用的审计方法**，不是一次性报告。每当改动提交路径、GC 路径或
副本读写路径时，按对应章节逐条过一遍。

判定标准只有一条：**宁可拒绝服务，不可静默破坏数据**。所有"读不到就当没有"、
"失败就跳过"的写法都是缺陷候选。

---

## 1. 删除路径（爆炸半径最大，先审）

`svnadmin gc` 是仓库里唯一主动删除数据的入口。每条 `Collect*` 支路都必须满足：

### 1.1 三条硬性规则

| # | 规则 | 反例（都是已修的真实缺陷） |
|---|---|---|
| 1 | 建立引用集时，**任何**读取失败都要向上传播 | `cdc.Parse` 失败静默跳过 → 该修订的 chunk 全部被当垃圾 |
| 2 | 必须区分"对象不存在"与"读取失败" | `loadSegmentIndex` 把 `ErrNotFound` 映射为空列表 → 索引丢失 = 整个 shard 被删 |
| 3 | 白名单必须**自校验覆盖范围** | keep-set 只看存在的条目，不校验是否覆盖到 HEAD |

### 1.2 检查方法

对每个 `Collect*` / `Compact*` 函数，搜这三个模式：

```bash
# 读失败被跳过（最可疑）
grep -n 'err != nil {' -A1 internal/fs/*.go | grep -B1 continue

# 错误被装饰成"无数据"
grep -n 'errors.Is(err, store.ErrNotFound)' -A2 internal/fs/*.go

# err == nil 里的静默分支
grep -n 'if .*; err == nil {' internal/fs/*.go
```

然后回答三个问题：

1. 读失败是否让整轮收集**拒绝执行**（而不是少删一点）？
2. "不存在"和"读失败"在返回值上是否可分？
3. 判断依据的白名单是否自身校验过完整性（如索引连续覆盖到 HEAD）？

### 1.3 当前状态

| 支路 | fail-closed | 守护测试 |
|---|---|---|
| `CollectTexts`（chunk manifest） | 是（`chunkScanOK`） | `TestCollectTextsKeepsChunksOfCorruptManifest` |
| `CollectTexts`（dir 表） | 是（`dirScanOK`） | — |
| `CollectTxnData`（activity manifest） | 是（返回错误） | `TestGCDeletionPathsRefuseOnReadFailure` |
| `CollectOrphanSegments`（keep set） | 是（要求连续覆盖） | `TestSegmentKeepSetRefusesLostIndex` |
| `CollectLoose`（仅删已打包 shard） | 是（`isPacked` 只缓存正结果） | — |

`TestSegmentKeepSetRefusesLostIndex` 在修复前必失败，可作为该测试有效性的证据。

### 1.4 演练要求

- GC 前先 `gc -dry-run`，观察 `orphans` 数量。**异常突增通常意味着索引或 manifest 损坏，而不是真的产生垃圾**。
- `verify --all-revs` 报 `segment index ... ends at N, HEAD needs M` 时，先 `repair --rebuild-index`，再跑 GC。修复前 GC 会拒绝执行，这是预期行为，不是故障。

## 2. 提交路径（原子性核心）

### 2.1 必须保持的顺序

```
lease → reconcileJournal → readCurrentStrict → ensureNoPendingPublication
      → OCC 检查 → 写数据对象 → 写 WAL → HEAD CAS → lease.Release
```

关键不变量：

| 不变量 | 位置 | 违反后果 |
|---|---|---|
| 分配 `head+1` 前确认没有该修订的 WAL 记录 | `ensureNoPendingPublication` | 覆盖另一修订的数据（split-lease 类） |
| 数据对象先于 HEAD CAS 落盘 | `putBatchObjects` / `publishSegmentPlans` | ack 后数据不可达 |
| CAS 失败时用 `journalOwns` 判定归属 | `wal.go:walRecordMatches` | 误判他人提交为自己的 |
| delta 提交要求 HEAD 节点与客户端 diff 起点**同一** | `commitTxn` OCC | 静默覆盖他人的 delete/re-add |

### 2.2 `CommitBatch` 的部分成功语义（易误用）

默认情况下 `CommitBatch` 逐条应用，**中间被拒不影响前后条目**：

```
revs=[2 0 3]  errs=[nil "out of date" nil]  err=nil  head=3
```

即：**修订号会出现空洞**。这是刻意的——服务端提交队列靠它让 disjoint 路径并发合并，
改成整批失败会退化成交互式提交互相打架。

**批量导入不能接受空洞**：dump 的修订连续且父修订编号固定，缺一个号就无法续传，
只能重建。因此 `CommitBatch` 提供 `AllOrNothing()`：

| 模式 | 调用方 | 中间失败的行为 |
|---|---|---|
| 默认（逐条） | 服务端提交队列、svn 客户端 | 前后条目照常发布，`revs` 出现 0 |
| `AllOrNothing()` | `svnadmin load` | 整批不发布，`revs` 全 0，返回整批错误 |

### `AllOrNothing` 实际保证什么（重要，别误读）

承诺的是**"不留空洞"，不是"绝不发布任何东西"**。两种失败阶段要分开看：

| 失败阶段 | 是否写了对象 | 结果 |
|---|---|---|
| 树校验失败 / 修订构建失败 | 否（rev-block 与树都在内存） | 仓库完全未变，`revs` 全 0 |
| WAL 写入中途失败 | **是**（记录逐条落盘） | 已写入的连续前缀会被 replay 发布，`revs` 仍全 0 |
| HEAD CAS 失败 | 是（数据对象/WAL 已写） | 未发布；若 peer 的 replay 抢先发布了我们的记录，`revs` 保留（确实成功） |

第二行是**不可回滚的**：WAL 记录是持久对象，删它们可能删掉别人已 ack 的记录，风险远大于收益。
所以不去删，而是靠 replay 的严格连续性兜住——`replayJournal` 只从 `head+1` 逐条推进，
遇到缺失或 `Parent != head` 立即停止，**永远只发布连续前缀**。结果是一个更短的批，不是空洞。

因此 load 的失败信息不写"nothing published"，而是报出实际 head：

```
dump: batch abandoned, target head is 4 (no gap introduced): ...
```

第三行是唯一"报告全 0 但实际部分成功"的反面情形，所以 CAS 分支必须逐组判定
`segmentOwns`：只有确认是我们的且已发布，才保留 `revs`；否则清零并报错。

守护测试：
- `TestPartialWalIsRolledForwardByReplay` —— v1 路径 WAL 部分写入后 replay 只发布前缀
- `TestAllOrNothingBatchLeavesNoHoleAfterPartialWal` —— 无修复时 `revs[0]=2` 谎报成功
- `TestSegmentBatchCasFailureReportsNothingPublished` —— segmented 路径 CAS 失败必须全 0

### segmented 与 v1 的差异

segmented 仓库**没有部分 WAL 的窗口**：一批只写一条 `journal/<first>` 记录
（`writeSegmentJournalBatch`），单次 Put 要么全成要么全败。v1 是每修订一条，
才有上表第二行。这也是推荐用 `create --segments` 建仓的又一个理由。

`load` 使用该选项，失败信息形如：

```
dump: nothing published (target head stays 0): fs: batch abandoned before
publishing (request rejected at request 1): fs: delete of nonexistent path ...
```

守护测试：
- `TestCommitBatchPartialFailureIsVisible` —— 默认语义（空洞可见）
- `TestCommitBatchAllOrNothingLeavesNoGap` —— 整批不发布
- `TestCommitBatchDefaultStillPartial` —— 确认服务端语义未被改动
- `TestLoadRejectsConflictingDumpWithoutPublishing` —— 无该选项时 head 会前进到 1，
  有该选项时保持 0

### 2.3 检查方法

改动 `commitTxn` / `CommitBatch` 后，跑：

```bash
go test -run 'TestCommitAtomicityUnderWriteFailures|TestLargeBatchReplayBeyondWindow' -race ./internal/fs/
go test -run TestChaosMatrix ./internal/fs/
```

混沌矩阵（`chaos_matrix_test.go`）覆盖：提交中掉副本、两副本全掉、rev-block 撕裂写。
新增故障模式就往矩阵里加一行。

## 3. 副本与租约路径

### 3.1 `QuorumGet` 的返回值必须被检查

`QuorumGet` 返回 `(value, count, err)`，其中 `count` 是**读到相同值的副本数**。
它不会因为 count 不足而报错，调用方必须自己判：

```go
b, count, err := qr.QuorumGet(ctx, key)
if err != nil { ... }
if count < quorum { /* 不可信 */ }
```

已检查的调用点：`lease.go:readOwn`、`releaseCommitLeaseQuorum`、
`mirror_reconcile.go`、`mirror_repair.go`。

`readLease` 只要求 `count >= 1` 是**刻意**的：它只用于"租约是否已过期"的快速判断，
真正的保护是随后的 `DeleteIfMatchQuorum`（条件删除 + quorum 门槛）。
ETag 不匹配时删除失败，所以读到陈旧副本不会误删有效租约。

### 3.2 检查方法

```bash
grep -rn 'QuorumGet(' internal/ --include='*.go' | grep -v _test
```

对每个调用点确认：`count` 是否参与判断？不参与的地方，是否有等价的条件写（CAS /
DeleteIfMatch）兜底？

## 4. 校验与可观测性

`verify --all-revs` 必须保持以下覆盖，缺一项就是盲区：

| 检查项 | 实现 |
|---|---|
| segment 索引连续覆盖到 HEAD | `verifySegmentIndexes` |
| segment 对象摘要 | `fullReads` + `verifySegmentFull` |
| 每个 chunk 的 sha256 + 整体 md5 + 总长 | `verifyNode` chunked 分支 |
| 外部文本流式 md5（O(1) 内存） | `verifyNode` TextRepExternal 分支 |
| 目录对象按内容哈希 | `verifyNode` KindDir 分支 |
| WORM 哈希链 | `VerifyJournalChain` |

改动上述任一分支后，`svnadmin verify --all-revs --texts` 必须仍能对
**故意损坏的对象**报出问题。测试方式：破坏一个对象，断言 verify 报告 Issue。

## 5. 已知的合理边界（不是缺陷，不要"修"）

写下来是为了避免后人误改：

- **`segmentEntryAt` 每次复制 block/props**：看似浪费，但不复制会让 `blockCache`
  里一个小条目持有整段 0.5 MiB 的底层数组，verify 2 万修订的仓就 OOM（有过事故）。
- **`readLease` 的 `count >= 1`**：见 3.1，条件删除兜底。
- **`CommitBatch` 部分成功**：见 2.2，服务端并发合并依赖它。
- **`deletePrimaryOrAll` 只删主副本**：standby 残留无害，镜像数千次删除会打垮 standby 写预算。
- **dump 尾部比头部慢约 4 倍**：祖先节点天然分散 + 每段都要解码校验，
  不是缓存策略问题（已实测排除 5 种方案，见《性能基线与回归.md》）。

## 6. 新增代码的自查清单

提交涉及数据安全的改动前，逐条确认：

- [ ] 任何 `continue` / 静默 `return nil` 都在"读失败但可以安全忽略"的位置，且注释说明了为什么安全
- [ ] 删除操作前，引用集/白名单的建立过程有任何读取失败都会中止整轮
- [ ] 白名单自校验了覆盖范围（不只是"存在的都收进来"）
- [ ] 新增的 `QuorumGet` 调用检查了 `count`
- [ ] 破坏一个对象的测试能证明对应的 verify 分支有效
- [ ] 如果改了 `commitTxn` / `CommitBatch`，`-race` 与混沌矩阵都跑过
- [ ] 新增的批量导入/回放调用方用的是 `AllOrNothing()`，而不是自己检查 `revs` 里的 0
- [ ] 新增代码没有依赖 `CommitBatch` 的默认部分成功语义，除非它确实需要 disjoint 合并
