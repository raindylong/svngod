# 性能基线与回归（2026-11-12，千万级修订能力线）

目的：为 scrub / WORM 哈希链 / GeoStore / ShardRouter 等近期功能建立提交吞吐基线，确认无性能回归，并为后续改动提供对照门槛。

## 环境

- 机器：ali-sa-sre001（x86_64，32 vCPU，overlay 文件系统）
- 后端：fake-s3 双节点（127.0.0.1:19001/19002，模拟 S3 主备 mirror）
- 工具：`cmd/revscale -store mirror -workers 8 -target 5000`（与 DAV MERGE 相同的 `CommitTxn` 路径）
- 对照版本：base = `9eaeffb`（scrub/WORM/geo/shard 之前）vs cur = `ffa89d4`（含全部功能 + 两轮 journal 缓存优化）
- 方法：交替 ×4 轮，每轮新建仓库（避免仓库增长污染），取分布

## 结果（mirror + quorum 2 路径，5000 修订/轮）

| 版本 | 各轮速率 (rev/s) | 均值 |
|---|---|---|
| base `9eaeffb` | 210.6 / 146.4 / 163.8 / 158.2 | ~161 |
| cur `ffa89d4` | 145.7 / 164.2 / 160.1 / 158.1 | ~157 |

**结论：功能全集（scrub 指标、WORM 链、props SHA、geo/shard 路由惰性存在）对提交吞吐无可测回归**（差异 <5%，在机器噪声范围内；base 首轮 210 为冷缓存异常值）。

文件存储对照（20k 修订，8 worker）：cur 211.6/s vs base 222.6/s —— 同样在噪声范围（无 journal 的控制路径不经过任何新代码）。

## 发现并修复的过程回归（已闭环）

第一轮测量发现 cur 比 base 慢 ~8%（~149 vs ~161 rev/s）。请求级 diff（fake-s3 访问日志逐键计数）定位到两个多余请求/提交：

1. **WORM 链 prev 读取**：`prevJournalSHA` 每次提交多读一次 `journal/<rev-1>`（`949f957` 修复：commit lease 保证连续修订，缓存上一条记录的编码字节，链哈希从内存计算；缓存未命中才回退 store 读取）
2. **回放 head 预取**：`replayJournal` 的 `journal/<head>` 预取每提交一次（`ffa89d4` 修复：head 记录正是本进程最后写的，走同一缓存）

修复后逐 rev 请求计数恢复 base 水平，交替四轮确认吞吐追平。

## 后续回归门槛（供 CI/手工对照）

- 同环境 `revscale -store mirror -target 5000 -workers 8` 新仓均值应 ≥ 150 rev/s
- 每 1000 提交的 mirror 主副本请求数（fake-s3 日志）应 ≤ 28（修复前 cur=28.1，base=26.8；当前已回到 ~27）
- 文件存储 20k 修订均值应 ≥ 200 rev/s

任何改动使提交路径新增 store 请求（尤其是逐提交的 Get/CAS）都会立即在这两个门槛上显形。

## 真实 S3 后端基线（RustFS 双实例，2026-11-12）

上面的基线跑在 fake-s3（本地进程，无网络）。本节记录真实对象存储上的数字，供容量规划与
"这是环境慢还是代码慢"的判定基线。

**环境**：`ali-sa-sre001`（32 vCPU），两个 RustFS 实例
（`192.168.23.228:9000` / `192.168.23.245:9000`，bucket `svn-ext`），quorum 2。

### 单次对象往返（`revscale -raw 50`，1 KiB）

| 端点 | Put 平均 | Get 平均 |
|---|---|---|
| 228 | 95–107 ms | ~1.0 ms |
| 245 | 148–201 ms | 1.8–4.2 ms |

**Put 比 Get 慢两个数量级**，这是本环境一切写入吞吐的根因（小对象写包含刷盘与元数据提交）。
任何"提升并发"的努力都受限于此：并发只能摊薄串行往返，不能降低单次 Put 成本。

### 提交吞吐

| 后端 | 配置 | 每次提交 | 速率 |
|---|---|---|---|
| 单 S3（无 WAL） | 1 worker | ~0.83 s | 1.2–1.3 rev/s |
| 双 S3 mirror | 1 worker | ~2.7 s | 0.4–0.5 rev/s |
| 双 S3 mirror | 4 / 8 / 16 worker | — | 0.8 / 0.9 / 1.0 rev/s |

**结论一：mirror(quorum 2) 的成本约为单库的 3.3 倍**，这是 WAL + 仲裁 + 双副本写入的固有代价，
不是回归——对照已确认单库路径同样受 Put 延迟支配。

**结论二：并发对 mirror 帮助有限**（0.5 → 1.0 rev/s，16 倍 worker 仅 2 倍吞吐）。原因是提交
被 commit lease 串行化（修订号连续性与跨分片批原子性的正确性要求，见
`internal/fs/lease.go`）。想要更高吞吐的正确方向是**提高单提交的批量**（group commit），
而不是增加 writer 数量——`revscale -batch N` 或服务端 `commit-batch`。

### 与 fake-s3 基线的关系

两套数字不可互相比较，也不应互相校验门槛：

| | fake-s3 | 真实 RustFS |
|---|---|---|
| mirror 均值 | ~157 rev/s | ~0.9 rev/s |
| 用途 | 检测**代码级**回归（每提交请求数、链缓存是否生效） | 容量规划、S3 故障演练 |

代码回归仍以 fake-s3 门槛为准（它去掉了网络与磁盘噪声，能把 ±1 个请求的差异显形）。
真实 S3 上的验证目标是**正确性**（备份/恢复/链校验/幂等），不是吞吐。

### 恢复演练在真实 S3 上的结果（`DRILL_MIRROR_FILE`）

| 修订数 | 全链路耗时 | 结果 |
|---|---|---|
| 40 | ~2 min | PASS（含 uuid 保持、链完整、re-dump 字节一致） |
| 150 | ~13 min | PASS（同上） |

耗时几乎全部是种子提交（0.5 rev/s），备份/恢复/校验本身很快。演练脚本默认 40 修订，
在真实 S3 上约 2 分钟，可接受作为发版前的必跑项。

## Group commit 在真实 S3 上的效果（2026-11-12）

背景：真实 S3 上 mirror(quorum 2) 单提交约 2.7 s，并发加 worker 几乎无效（commit lease 串行化）。
那两个杠杆只剩"增大单次提交的批量"。本节是实测。

**环境**：同上（两台 RustFS，bucket `svn-ext`，quorum 2），每次独立新仓，目标 200 修订。

| 存储格式 | batch | worker | 速率 | 相对 batch=1 |
|---|---|---|---|---|
| v1 (per-revision) | 1 | 4 | 0.7 rev/s | — |
| v1 | 20 | 4 | 4.2 rev/s | **6.0×** |
| v2 (segments) | 1 | 4 | 0.6 rev/s | — |
| v2 | 20 | 4 | 12.1 rev/s | **20×** |
| v2 | 50 | 4 | **33.4 rev/s** | **~50×** |

全部配置 `verify --all-revs` 与 `verify --all-revs --texts` 均无问题。

### 为什么 v2 远好于 v1

一批 N 个修订的写入次数：

| | v1 | v2 (segments) |
|---|---|---|
| 修订数据 | 2N 次 Put（rev-block + props） | **1** 次 Put（整批一个 segment） |
| WAL | N 条记录 | **1** 条记录 |
| HEAD 发布 | 1 次 CAS | 1 次 CAS |
| commit lease | 1 次 | 1 次 |

v2 把每批压到常数次往返，v1 仍随 N 线性增长，所以 v2 的 batch 收益能持续到 50+，
v1 在 batch≈20 附近就饱和（~5 rev/s）。

**运维结论**：真实 S3 后端应使用 `--segments` 建仓 + 服务端
`commit-batch`（`-commit-batch N`）或客户端批量提交。默认 batch=1 的 v1 仓库在
WAN 延迟下只有 0.6–0.9 rev/s，不适合大批量导入。

### 附带修掉的两个 v2 缺陷

压测 v2 时 `verify` 直接报错，暴露了两个此前没有被真实数据触发的问题：

1. **链校验器不认批量记录**：v2 一批只写一条覆盖 `[First, First+Count)` 的记录，
   `VerifyJournalChain` 逐 rev 走，把 First+1 当成"链断裂"。结果是**所有 v2 库都 verify 失败**，
   连带 `dump --verify` 拒绝备份——门禁把健康库也拦了。
2. **v2 记录从未设置 `PrevJournalSHA`**：批间无链接，篡改检测在 segmented 库上实际失效。
   前驱不是 `journal/first-1`（批量场景下该 rev 没有记录），而是"覆盖 first-1 的那条记录"。

两条都已修复并有回归测试（`TestSegmentedBatchChainVerifies`、
`TestDumpVerifyAcceptsGroupCommittedSegments`）。

## `svnadmin load` 接入批量提交（2026-11-12）

`load` 原先每修订调用一次 `CommitTxn`，在真实 S3 上等于每修订付一次
lease + WAL + HEAD CAS。改为缓冲后用 `CommitBatch` 提交（默认 256，`--batch N` 可调）。

**环境**：两台 RustFS，quorum 2，源仓 1000 修订（`revscale -batch 50 -mixed`），
dump 348 KB，目标仓一律 `--segments`。

| load --batch | 耗时 | 速率 | 相对 batch=1 |
|---|---|---|---|
| 1（旧行为） | **2093.9 s（34.9 分钟）** | 0.48 rev/s | — |
| 32 | 73.5 s | 13.6 rev/s | 28.5× |
| 64（旧默认） | 33.8 s | 29.6 rev/s | 62× |
| 200 | 12.6 s | 79.5 rev/s | 167× |
| 256（新默认） | ~13 s | ~77 rev/s | ~160× |
| 500 | 5.8 s | 172 rev/s | 361× |

**正确性证据**（比耗时更重要）：源仓与 `batch=1 / 32 / 64 / 200 / 500` 五个恢复仓
各自重新 dump，**sha256 全部相同**（`f82d9039…f2f4`），且每个仓
`verify --all-revs --texts` 干净、`journal hash chain intact (revs 1..1000)`。
批量与顺序导入的结果不可区分。

### 批量暴露并修掉的两个缺陷

批量提交一组的**相互依赖**修订（增量导入的本质：rev N 建立在 N-1 上），暴露出两个
此前逐条提交时不会触发的问题：

1. **批内无法解析刚创建的节点**：`ensureDir` 按 NodeID 读 store，而该修订尚未发布
   → `store: object not found`。`CommitBatch` 现在把本批构建的节点留在
   `pendingNodes`，`GetNodeRev` 先查它再查 store。
2. **目录属性修改会回滚同批的子项修改**：`applyChange` 的目录 modify 分支整份复制
   `old.children`，把同一次提交里先做的子文件修改覆盖回去（dump 会把"改文件"和
   "改父目录属性"放在同一修订里，顺序还不固定）。改为合并而非覆盖。

二者都会**静默损坏数据**（第二种是内容悄悄回到旧版本），因此回归测试按"先创建后修改"
两种顺序断言每修订的内容与目录属性。

### 与恢复 SOP 的关系

《备份与恢复SOP.md》原先写明 `load` 逐修订提交、大仓恢复慢是已知上限。该上限已解除：
同一 1000 修订的恢复从 34.9 分钟降到约 13 秒。**百万修订量级未实测**，仅按每千修订
的实测值线性外推会忽略内存占用与 CAS 冲突概率的变化，实际部署前应在目标数据量上标定。
默认值 256 是吞吐与内存的平衡（一批的 rev-block 需同时驻留内存），`--batch 1` 可退回旧行为。
